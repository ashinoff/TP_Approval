Актуализация DOCX-этапа 01.11.2026: визуальные замечания хранятся в тех же comments с прежней связью task/version, поэтому счётчики матрицы/реестра учитывают их до решения и после него. Автор сохраняется в author_snapshot при создании, не только в будущем решении. Вкладка матрицы сохранена, маршруты/замещения/исторические циклы прежние. Новые проверки — DOCX_PROTOTYPE.md и PROGRESS.md.

## Как открыть
На локальном стенде http://127.0.0.1:5173 войти пользователем своего РЭС либо центрального подразделения, открыть акт и выбрать «Матрица согласования». TECH_ADMIN автоматического доступа к содержимому не получает. На узком экране таблица прокручивается по горизонтали внутри карточки.

Строки: Начальник РЭС с названием конкретного РЭС, СУЭ, СТП, ГИ. Колонки: подразделение, ФИО, статус, поступление, сохранённый норматив/предельная дата, решение, фактическая продолжительность, замечания. Даты — Europe/Moscow. У начавшегося этапа норматив берётся из policy_id задачи, не из текущей новой настройки. До создания задачи поля назначения/дат/норматива пусты: будущий исполнитель и срок не выдумываются.

Нажатие на ненулевое число замечаний открывает только замечания соответствующей задачи выбранного цикла. Нулевой счётчик неактивен. Историческое замечание остаётся у исходной версии/задачи; исправление и подтверждение видны в обычной вкладке документа, не переносятся как новое замечание в следующий цикл.

## Статусы
| Данные БД | Строка матрицы | Индикация |
|---|---|---|
| Решение APPROVE | Согласовано | ✓ зелёный |
| Решение RETURN | Отклонено с замечаниями | ✕ красный |
| OPEN задача в открытом цикле | Ожидает решения | ◷ жёлтый |
| Задача не создана | Этап не начался | ○ серый |
| Завершена/отменена без решения | Без решения · сбор закрыт | ⊘ серый |

Просрочка отмечается отдельно: ⏰ «Просрочено» для действующей задачи или «Завершено с просрочкой» для завершённой. Отсутствие решения никогда не преобразуется в APPROVE. Для cancelled-задачи дата решения остаётся пустой, а длительность фиксируется на completed_at/closed_at.

Общий итог относится **к выбранному циклу и его публикации**. Приоритет отображения: REVOKED публикация → «Отозвано»; APPROVED цикл → «Согласовано»; просроченная открытая задача → «Просрочено»; RETURN/RETURNED цикл → «Требует доработки»; иначе «На согласовании». Если возврат и просрочка есть одновременно, дополнительно показывается «Требует доработки». Для неподанного черновика итог «На согласовании» сопровождается явным пояснением, что документ ещё не направлен и все этапы не начались. Согласование в сроках/с опозданием не изменяет решение специалиста.

## Циклы, версии и обновление
Показаны номер Word-версии выбранного цикла и номер цикла. «Текущий цикл» означает последний поданный цикл; неподанная новая версия не подменяет его. Если версия уже создана, но не подана, показан её номер отдельно. Для UNDER_REVISION есть пояснение о пересмотре прежней утверждённой публикации.

Можно выбрать любой прошлый цикл. Вкладка и выбор цикла сохраняются в sessionStorage как UI-предпочтения; JWT и данные документов туда не записываются. После F5 и входа пользователь открывает акт снова и получает те же выбранные исторические данные из БД.

Пока вкладка видима, один GET выполняется раз в 5 секунд; при возврате фокуса/видимости — сразу. Параллельные запросы не запускаются, старый ответ при смене акта/цикла отбрасывается. Есть «Обновить матрицу». Обновляется только матрица, без reload страницы. При ошибке права/сети прежние данные не выдаются за актуальные. Это polling, не WebSocket/SSE и не гарантированная мгновенная доставка.

## API
`GET /api/v1/acts/{actId}/approval-matrix?cycleId={uuid}`

Bearer JWT + обычная внутренняя учётная запись. cycleId необязателен (последний цикл), при выборе другой/несуществующей принадлежности — 404. Чужой акт и TECH_ADMIN без отдельной бизнес-роли — 404; без токена — 401; некорректный UUID — 422.

Ответ: actId/resName/asOf/actState; cycle, version, latestVersionNumber; список cycles с номерами версий; overall, overdue, requiresRework, publicationStatus; ровно четыре rows.

Строка: role/department/taskId, person, assignment, substitution, status, receivedAt/dueAt/decidedAt/completedAt, policy(id/workingDays/preliminary), elapsedSeconds/durationRunning, overdue/wasOverdue, commentCount и comments(id/task_id/versionId/authorId/text/createdAt).

Все данные для ответа читаются **одним SQL statement**: одна согласованная PostgreSQL snapshot при конкурирующих решениях. RLS app.acts и дочерних таблиц применяется под tp_runtime. SECURITY DEFINER helper matrix_task_identity проверяет app.can_read(res_id), не даёт обхода RLS и не раскрывает произвольный справочник пользователей. GET не пишет аудит/уведомления и не меняет процессы.

## История и миграция 005
Миграция добавляет в tasks только assignment_snapshot и completion_snapshot. Первый хранит назначенного сотрудника и основного владельца роли; второй — фактического исполнителя/сотрудника при закрытии. Для принятого решения ФИО и ID берутся из существующих immutable decisions.actor_name/actor_id.

BEFORE trigger фиксирует сведения при создании/смене назначения и завершении задачи. После закрытия задача защищена от изменения; существующие команды изменяют только OPEN-задачи, поэтому переходы workflow остались прежними. Это не копия статуса, а сохранение идентичности человека. Будущее изменение норматива/профиля/окончание замещения не меняет данные завершённой строки.

Для записей до миграции: фактическое ФИО решения уже сохранено в decisions и используется достоверно. Если решения не было, историческое ФИО замещавшего сотрудника невозможно восстановить из отсутствующих записей: используется явно помеченное LEGACY_ASSIGNEE исходное назначение по доступному профилю, UI показывает пояснение. Назначение до миграции помечено LEGACY_CURRENT_PROFILE. Нельзя утверждать, что эти старые недостающие сведения восстановлены точно.

Продолжительность — **календарные секунды** от received_at до decided_at, completed_at либо closed_at; для OPEN — до asOf ответа. Для завершённых строк она не растёт. Это не расчёт рабочего времени по часам: рабочие интервалы ещё не утверждены. Норматив и due_at остаются штатными рабочими днями/календарём задачи.
