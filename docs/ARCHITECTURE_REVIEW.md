# Проверка проекта архитектуры

31.10.2026. Первоначальный анализ сценариев дополнен реализацией ядра: выполнены 16 интеграционных групп на настоящем PostgreSQL 17.11 и 3 группы тестов DOCX/JWT/JWKS. Точный проверенный объём — CORE_STATUS и PROGRESS. Разделы про редактор, callback, ТУ, сервисный API и production остаются требованиями, а не завершёнными проверками.

## Транзакции и параллелизм
Команда решения: BEGIN → проверить пользователя/область → заблокировать строку цикла SELECT FOR UPDATE → заблокировать задачу в том же порядке → перепроверить назначение/версию/состояние → записать единственное решение → закрыть задачу → пересчитать результаты всех задач → выполнить переход → записать audit/outbox → COMMIT. Все пути изменения цикла используют один порядок блокировок. READ COMMITTED с этой сериализацией допустим; при SERIALIZABLE реализовать ограниченные повторы.

| Сценарий | Ожидаемый результат / защита |
|---|---|
| Три одновременных APPROVE | Последний сериализованный запрос видит три решения; один release, одна группа финальных событий |
| RETURN одновременно с последним APPROVE | После блокировки пересчёт видит возврат; APPROVED невозможен |
| Первый RETURN, остальные ещё работают | CENTRAL_COLLECTING, их задачи сохраняются; новая подача запрещена |
| Двойной клик/сетевой повтор | idempotency key + unique(task_id) не создают два решения/перехода |
| Решение старой версии | Конфликт version/cycle/task; никакого переноса в новый цикл |
| Одновременная подача двух версий | Блокировка акта + partial unique активного цикла; только одна успешна |
| Переназначение одновременно с решением | Та же блокировка задачи и перепроверка assignee; старый исполнитель не проходит |
| Замечание одновременно с APPROVE | Оба пути блокируют cycle/task; новое замечание после закрытия задачи отклоняется |
| Запоздалый callback редактора | Только производный artifact своей сессии; не перезаписывает исходную версию или решение |
| Повторный callback/outbox/job | Уникальный ключ и идемпотентная обработка; новые бинарные объекты только append |
| Сбой между PostgreSQL и хранилищем | Файл сначала карантин/READY, затем DB-ссылка; осиротевшие объекты собираются после grace period, не удаляя используемые версии |
| Падение после COMMIT до уведомления | Outbox остаётся в БД, worker повторяет; событие не теряется |
| Один центральный участник не ответил | Цикл остаётся открыт, срок и эскалация работают; автоматического решения за человека нет |

По уточнению пользователя PROCESS_ADMIN своей области вправе закрыть сбор после просрочки оставшихся задач с причиной; это реализовано и проверено. Отсутствующие решения не становятся APPROVE. Подача поверх открытого цикла запрещена.

## Изоляция доступа
- Пользователь Адлерского РЭС не получает чужой акт через список, прямой ID, версии, комментарии, editor config, download, job, печать, Excel или агрегаты. Тестировать также сообщения ошибок, totals и ссылки в уведомлениях.
- RLS проверять реальным runtime SQL, не только mock репозиторием: отсутствие app.user_id, неверный РЭС, очистка контекста пула, INSERT/UPDATE WITH CHECK, views/joins и отдельные service-права.
- Не принимать res_id/actor_id/assignee из недоверенного payload без серверного разрешения. Видеть документ не равно иметь право согласовать его.
- Сервис учёта ПУ не может читать черновые версии или пользовательские API и не обходит область РЭС. Неоднозначность не разрешается случайным первым результатом.
- Деактивация пользователя/снятие роли должны действовать при следующем запросе несмотря на ещё действующий JWT. Активные задачи требуют контролируемого переназначения.
- RLS не заменяет проверку хранилища: документы не имеют постоянных публичных URL. Временный доступ редактора ограничен файлом, сроком и сессией.

## История и целостность документов
- Оригинальный DOCX, версии ТУ, технические поля и связи фиксируются в снимке подачи. Конвертация и комментирование пишут производные копии.
- Замечание принадлежит точной версии; нет автоматического переноса якоря/согласования. Исправление имеет отдельное событие с target_version_id.
- Изменение названия категории/подразделения/ФИО не переписывает прошлые листы согласования благодаря снимкам.
- Release и пакет печати сохраняют хеши, источник и версии генератора/шаблона. Просмотр новой версии не меняет прошлую публикацию.
- ONLYOFFICE необходимо проверить прототипом: сохранность таблиц/полей/шрифтов, синхронизация категории/якоря и автора, параллельные копии, callback после решения, работа внутри sandbox. Не обещать готовность до проверки.
- Подтверждение исправлений автором, пересмотр через новый цикл и отзыв PROCESS_ADMIN реализованы явными командами; детали фактического объёма в CORE_STATUS. Категории и Word-якоря ещё требуют этапа 3.

## Сроки и уведомления
- Снимок policy/calendar делает due_at воспроизводимым. Переход года без утверждённого календаря должен выдавать явную ошибку настройки, не считать дни приблизительно.
- Норматив и календарь изменяются версией; ретроактивный пересчёт отдельной командой с причиной. Проверить переносы рабочих суббот, праздники, сокращённые дни и поступление вне интервалов.
- Warning/overdue/escalation дедуплицируются по task/policy событию/recipient. Параллельные scheduler-worker используют lease/блокировку, но доставка всё равно at-least-once с дедупликацией.
- Badge считает персональные задачи по текущим назначениям/правам, не уведомления всех участников. Чтение сообщения не меняет согласование.
- Метрики не суммируют длительности параллельных этапов и не удваивают замечания из-за истории событий.

## Контроль перед эксплуатацией
Интеграционные/конкурентные тесты на PostgreSQL; e2e полного цикла и возврата; враждебные файлы/SSRF; JWT и origin/source; восстановление backup; нагрузка; лицензии и ресурсы редактора; мониторинг очередей; согласование политики ПДн. Эти проверки ещё не выполнены.

Вывод: проект предлагает меры против гонок, межрайонного доступа и потери истории. Остаются явные бизнес-вопросы и технический прототип редактора; объявлять систему проверенной или готовой к эксплуатации нельзя.
