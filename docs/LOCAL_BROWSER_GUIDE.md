# Локальный тестовый стенд TP_Approval

Проверен 31.10.2026 в настоящем Google Chrome (headless, отдельные профили Playwright). Production Keycloak, Amvera, SUE_system и существующие базы не подключались. Использованы только учебные пользователи, адреса и DOCX.

## Открыть сейчас

**Интерфейс: http://127.0.0.1:5173**

На экране должен быть жёлтый баннер «Демонстрационный стенд». Выберите пользователя и нажмите **«Войти в тестовый стенд»**. Пароль для этих синтетических аккаунтов не нужен. Для смены роли нажмите **«Выйти»**, затем выберите другого пользователя. JWT хранится только в памяти: после F5 нужно снова выбрать пользователя, данные документов сохраняются в PostgreSQL.

Используйте именно `127.0.0.1`, а не `localhost`: тестовый сервис входа разрешает точный origin `http://127.0.0.1:5173`.

| Сервис | Адрес |
|---|---|
| Интерфейс React/Vite | http://127.0.0.1:5173 |
| API Express | http://127.0.0.1:3000 |
| Проверка доступности API | http://127.0.0.1:3000/health |
| Проверка соединения с БД | http://127.0.0.1:3000/ready |
| Локальный тестовый JWT/JWKS | http://127.0.0.1:4100/jwks |
| Изолированный PostgreSQL 17.11 | 127.0.0.1:55432, БД `tp_approval_demo` |

Все сервисы слушают только loopback. Тестовый JWT-сервис подписывает RS256 токены, API проверяет их через HTTP JWKS, issuer/audience/срок/роль обычным механизмом. Это имитация **только провайдера входа**, а не маршрута согласования или БД. Боевой Keycloak и SSO оболочки этой проверкой не проверяются. У production API нет автоматического доверия к тестовому issuer.

## Пользователи

| Выбор на экране | Тестовый subject | Область |
|---|---|---|
| Начальник РИРУ · Адлерский РЭС | `riru-adler` | Адлерский РЭС |
| Начальник РЭС · Адлерский РЭС | `chief-adler` | Адлерский РЭС |
| СУЭ | `sue` | Все РЭС, решение только за СУЭ |
| СТП | `stp` | Все РЭС, решение только за СТП |
| ГИ | `gi` | Все РЭС, решение только за ГИ |
| Технический администратор | `tech` | Нет автоматического доступа к актам |
| Администратор процесса | `process` | Явное глобальное управление процессом |
| Начальник РИРУ · Хостинский РЭС | `riru-hosta` | Хостинский РЭС |
| Начальник РЭС · Хостинский РЭС | `chief-hosta` | Хостинский РЭС |

Все отображаемые имена начинаются с «Демо». Системный администратор не может согласовывать акт вместо специалиста. Отдельного полноценного интерфейса администрирования пока нет; административные методы существуют на сервере.

## Повторно запустить или остановить

В PowerShell:

```powershell
cd 'C:\Users\User\codex\проекты\TP_Approval'
npm.cmd run demo
```

Если стенд уже запущен, команда сообщит о занятых портах и **не подключится** к чужому сервису. Для остановки существующего стенда в другом терминале:

```powershell
npm.cmd run demo:stop
```

Дождитесь остановки, затем снова `npm.cmd run demo`. Для foreground-запуска также работает Ctrl+C. База при остановке не удаляется, повторный запуск не очищает документы. В этой сессии стенд оставлен в фоне для вашей проверки. После перезагрузки компьютера его нужно запускать заново.

Стенд не требует `.env`, не читает DATABASE_URL/MIGRATION_DATABASE_URL и не использует установленный системный PostgreSQL. Он создаёт собственный cluster из закреплённого npm dev-пакета в `%TEMP%\tp-approval-demo-*`; путь и случайные секреты хранятся в `.local/demo.json`. Не редактируйте этот файл и не добавляйте `.local` в Git. Файлы документов — `.local/demo-storage`, логи фонового запуска — `.local/demo.stdout.log` и `.local/demo.stderr.log`. Для полностью нового стенда не удаляйте данные во время работы; штатная команда сброса пока не предусмотрена.

Если отсутствуют зависимости: `npm.cmd ci`. Для генерации учебных DOCX:

```powershell
& 'C:\Users\User\codex\.venv\Scripts\python.exe' scripts/create-demo-documents.py
```

Python-скрипт использует python-docx, создаёт только два синтетических файла. Microsoft Word GUI при автоматической проверке не запускался: проверялся DOCX-формат, загрузка/скачивание и сохранность байтов.

## Полный ручной сценарий

В каждой карточке теперь есть вкладка **«Матрица согласования»**. Выберите её, чтобы видеть Начальника РЭС/СУЭ/СТП/ГИ, ФИО, сроки, решения, замечания и историю циклов. Изменения другой сессии появляются автоматически в течение 5 секунд без F5. Нажмите число замечаний для просмотра, выберите прошлый цикл в списке. Для принятия решения вернитесь во вкладку «Документ и замечания». На мобильном таблица прокручивается горизонтально. Подробности: [APPROVAL_MATRIX](APPROVAL_MATRIX.md).

1. Войдите как РИРУ Адлерского РЭС. Раскройте «Создать акт». Заполните уникальный номер договора и акта, дату, условного заявителя и адрес. Нажмите «Создать карточку».
2. В карточке через «Новая версия DOCX» выберите `.local\demo-documents\act-v1.docx`. Это учебный акт с таблицей и ошибочной мощностью 150 кВт. Нажмите «Направить Начальнику РЭС».
3. Выйдите, войдите Начальником РЭС Адлерского РЭС. Откройте акт через «Мои задачи» или реестр. Проверьте срок. Выберите «Согласовать», сохраните решение.
4. Войдите как СУЭ. Убедитесь, что badge/«Мои задачи» содержит акт. Выберите «Вернуть с замечанием», напишите «Мощность 150 кВт нужно исправить на 15 кВт», сохраните. Акт переходит в «Сбор замечаний».
5. Поочерёдно войдите как СТП и ГИ, откройте акт и согласуйте. Они продолжают проверять независимо от возврата СУЭ. Только после завершения всех трёх проверок акт станет «На доработке».
6. Войдите как РИРУ. Проверьте задачу доработки, срок и красное замечание с именем автора. Загрузите `.local\demo-documents\act-v2.docx`, в котором указано 15 кВт. Можно вместо готовой v2 открыть v1 в Word, исправить значение и сохранить под новым именем, затем загрузить его.
7. Нажмите «Указать исправление», заполните пояснение и «Сохранить отметку». После этого направьте новую версию Начальнику РЭС.
8. Начальник РЭС повторно согласует документ. Старые решения остаются историей, новый цикл начинается заново.
9. СУЭ открывает акт, нажимает «Подтвердить устранение», заполняет результат проверки и сохраняет отметку. Замечание становится зелёным. Затем СУЭ согласует новую версию. Попытка согласовать до подтверждения показывает понятную ошибку и не записывает решение.
10. СТП и ГИ согласуют новую версию. Итог — зелёный статус «Согласовано», две версии, два цикла и история всех решений.
11. Скачайте обе версии DOCX. Обновите страницу, войдите повторно и откройте акт: документы, замечание, пояснения и решения должны остаться.
12. Войдите пользователем Хостинского РЭС или техническим администратором: созданный адлерский акт отсутствует. Прямые запросы к карточке и файлу с их JWT возвращают 404.

При работе в разных вкладках нажимайте «Обновить данные»: серверная история постоянна, но автоматического realtime-обновления других вкладок пока нет. Закрытие задачи и прочтение уведомления — разные действия. Один акт не считается несколько раз из-за повторных уведомлений или просрочки.

## Что реально проверено автоматически

`npm.cmd run test:browser` запускает **настоящий headless Chrome**, 9 отдельных сессий и полный цикл выше. Дополнительно проверяет ошибочный DOCX, запрет раннего согласования до подтверждения замечания, приватность карточки/файла/чужого уведомления, badge всех пользователей, скачивание DOCX с SHA-256, отдельную учебную просрочку/эскалацию и мобильный viewport 390×844. Прогон не очищает существующие тестовые акты; счётчики проверяются относительно исходного состояния.

Пример успешного результата — `.local/browser-report/result.json`, 16 групп, `failures: []`, Chrome `156.0.8078.48`. Проверенный акт **БРАУЗЕР-1793476608991** можно открыть под РИРУ Адлерского РЭС. Снимки `01–09` находятся в той же папке. Браузерные ошибки JavaScript отсутствовали. При первых прогонах найдены неоднозначное доступное имя поля «Решение» и лишние запросы UI, вызывавшие 429 при интенсивной работе; исправлено без отключения лимитов, итоговый повторный прогон прошёл.

После реальной остановки и повторного запуска PostgreSQL/API/JWT/Vite дополнительно выполнено `npm.cmd run test:browser:persistence`: новый Chrome подтвердил сохранность APPROVED, двух версий, двух циклов, восьми решений и двух событий замечания. Отчёт `restart-result.json`, снимок `10-after-service-restart.png`.

Сборка frontend/backend, 3 группы unit/security и 16 интеграционных групп PostgreSQL также прошли. В реестре останутся документы `БРАУЗЕР-*` и `СРОК-*`: это учебные результаты прогонов. `СРОК-*` оставлен специально просроченным для проверки отображения у Начальника РЭС.

## Ограничения

Нет боевого Keycloak, проверки SSO в iframe SUE_system, ONLYOFFICE, просмотра содержимого Word внутри приложения и привязки замечаний к фрагментам. Замечания пока текстовые, относятся к версии. PDF/ТУ, категории ошибок, печать, внешний lookup, аналитика и автоматический scheduler ещё впереди. В тестовом стенде без ClamAV выполняется структурная проверка DOCX; реальные документы и персональные данные сюда не загружать. Календарь намеренно учебный, только будни, а не официальный производственный календарь.
