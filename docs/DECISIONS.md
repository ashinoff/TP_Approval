# Архитектурные решения

## 04.11.2026 — Email и жизненный цикл локальной учётки
По запросу пользователя email хранится в app.users, нормализуется trim/lowercase и уникален среди неудалённых профилей. Новое создание/редактирование требуют валидный email; старые строки и bootstrap-администратор остаются с NULL до ручного заполнения. Email — подготовка к отдельной привязке Keycloak, он не заменяет issuer/sub и сам по себе не даёт вход или роли.
Редактирование профиля выполняется атомарно по account_revision, сохраняет пользовательский UUID и не переписывает прошлые решения/снимки имён. Смена логина/email/назначений отзывает сеансы. Удаление освобождает логин/email и удаляет парольные учётные данные/сеансы, но оставляет неактивного пользователя для внешних ключей и истории; повторно созданная учётка имеет новый UUID. Исторические назначения сохраняются с revoked_at; права, кандидаты и новые назначения используют только действующие роли. Открытые задачи и действующие/будущие замещения блокируют удаление соответствующей роли/учётки. Свою учётку удалить или снять у себя глобальный TECH_ADMIN нельзя; изменения и выдача задач сериализуются общей блокировкой. Это не меняет бизнес-маршрут и не выполняет согласование/переназначение за сотрудника.

## 04.11.2026 — Пароль подключения к БД задаёт пользователь
Пользователь прямо потребовал сохранить ранее выбранные пароли. Отдельный минимум16 символов, добавленный в setup-standalone, отменён: подготовка принимает непустой пароль из DATABASE_URL и устанавливает его роли tp_runtime. Это решение относится только к подключению PostgreSQL; минимальная длина веб-пароля12символов, первая смена, scrypt, CSRF и сессии не меняются. Разделение служебного владельца и runtime сохраняется: использовать существующего admin/суперпользователя как HTTP-роль нельзя. Цена совместимости — отсутствие дополнительного контроля длины пароля БД в приложении. Пароли остаются настройками окружения, реальные значения не включаются в код/документацию/тесты.

## 04.11.2026 — Рабочий самостоятельный вход перед SSO
Пользователь прямо отложил платформенную интеграцию и выбрал реальную работу вместо демостенда. Принят отдельный AUTH_MODE=local с личными логинами/паролями, а не публикация локального JWT-демо. Пароли — scrypt (N32768/r8/p3, случайная соль16байт); сессии — случайный256-битный токен, его SHA-256 в БД, срок8часов. Production cookie HttpOnly/Secure/SameSite=Strict; запросы записи требуют Origin и CSRF. После выдачи/сброса временного пароля API требует его заменить; смена пароля, блокировка и выход отзывают соответствующие сессии. Роли/РЭС остаются в прежней БД и проходят прежние проверки.
Локальные учётные данные вынесены в отдельные закрытые таблицы миграции015, issuer локальных пользователей urn:tp-approval:local. Слияния с существующими Keycloak-пользователями по совпадению имени/логина нет: будущая миграция идентичности должна явно сохранять пользовательский UUID и историю.
Первичная подготовка получает отдельно служебный URL и runtime URL, проверяет совпадение базы, создаёт первый TECH_ADMIN только при отсутствии локальных учётных записей. Повторная подготовка не меняет существующий пароль. Постоянное хранилище /data/storage; entrypoint подготавливает том и запускает API от node, удаляя из его окружения bootstrap-секреты.
Отсутствие ClamAV больше не блокирует открытие интерфейса, но блокирует обе точки загрузки в production до записи данных. Проверка содержимого и антивирус не отменены. Это позволяет сначала настроить вход/пользователей, не превращая приложение в открытый демостенд. Для фактического согласования остаются обязательны сканер, назначения и утверждённый календарь. Самостоятельный UI календаря и удаление прежних назначений не входят в этот этап.
Статус: реализация, локальные проверки и штатный GitHub CI завершены успешно (подробности PROGRESS; запуск41807277699 на5c08b46): нативная PostgreSQL17.11, Chromium с HTTPS и перезапуском БД/API, сборка Docker. Пользователь поручил самостоятельно выполнить действия в GitHub, включая обновление main после проверок; публикация оформлена PR №2. Сборка образа не равна приёмке развёртывания: настройка Amvera, постоянный том и живой ClamAV ещё не проверены.

## 04.11.2026 — Принято (Р4): ручное подтверждение спорных пунктов сверки инженером
Открытый вопрос из ENGINEER_WORKSPACE.md закрыт так: MANUAL_REVIEW и UNKNOWN подтверждает Инженер РИРУ своего РЭС с обязательным комментарием (не короче 10 символов) в отчёте текущей версии и ТУ; подтверждение неизменяемо и видно всем согласующим, прежде всего Начальнику РИРУ. DIFFERENCE подтвердить нельзя — только исправить документ. Новая версия, другие ТУ или новые правила дают новый отчёт; прежние подтверждения на него не переносятся. Категория надёжности показывается только для сведения (INFO) и отправку не блокирует. Решение взято из docs/codex/CODEX_PROMPTS.md, раздел «Решения пользователя»; при несогласии пользователя менять API/миграцию следующей миграцией, 014 после применения не редактировать.

## 03.11.2026 — Принято: одна кнопка, необязательные реквизиты и подготовка ТУ
По последнему уточнению пользователя пакет можно сохранить, если из ТУ распознан номер договора, без обязательного ручного заполнения остального. Дата договора NULL, а не фиктивная текущая дата; миграция 013 сохраняет неизменность существующей идентичности и NULL-aware уникальность. Подготовка ТУ до импорта удаляет исключительно file/attachedTemplate, с уведомлением и строгой проверкой копии; прочие внешние связи не разрешены. Исходный файл пользователя и поданные версии не переписываются. JSZip 3.10.2 закреплён как прямая зависимость (раньше транзитивная через docx-preview). Пользователь отдельно разрешил push кода и контекста, без деплоя/публикации ПДн.

## 03.11.2026 — Принято: создание документа из ТУ и пакет договора
По прямому заданию пользователя форма «Создать документ» заполняется из ТУ; номер нового документа равен номеру договора. Имена файлов — номер + АКТ ТП/АВТУ/ТУ. UUID и история старых документов не переписываются. Общий пакет использует contracts и отдельные редакции ТУ/акта без объединения act_id. Текущая дата — дата создания, неизвестная дата договора не выдумывается. Локальное извлечение не заменяет сверку перед submit. ТУ доступны для просмотра; замечания и решения относятся только к акту. Дополнительные вложения пока не реализованы. См. TU_IMPORT.md.

## 03.11.2026 — Принято: меню инженера и обязательная сверка ТУ
По прямому заданию пользователя введены четыре раздела инженера и блокирующая серверная проверка перед отправкой. Выборки/счётчики основаны на БД и действующих публикациях, область РЭС не меняется. Immutable отчёт привязан к версиям, ТУ, хешам и правилам; прямой submit не обходит проверку. История/существующие публикации не пересматриваются автоматически. Строгие правила ограничены пятью реквизитами, не универсальной экспертизой; UNKNOWN/MANUAL_REVIEW блокируются до определения ручного порядка. Маршрут человеческих согласований сохранён. Подробности и ограничения — ENGINEER_WORKSPACE.md и PROGRESS.md.

## 02.11.2026 — Принято пользователем: отдельный инженер и первый этап РИРУ
Основание — прямое уточнение пользователя: загружает Инженер РИРУ своего РЭС; первый согласующий Начальник РИРУ того же РЭС, второй Начальник РЭС, затем параллельно службы. В UI ГИ называется ТЕХБЛОК, код GI сохраняется для совместимости. Реализован новый маршрут version=2; вместо переписывания старой истории введён workflow_version цикла. Действующие/закрытые прежние циклы version=1 не дополняются фиктивными решениями; новая отправка использует version=2. Назначения прежнего загрузчика мигрируют в RIRU_ENGINEER с прежними UUID/замещениями, новый руководитель назначается отдельно. Правила доступа, самосогласования, параллельного сбора, версий, badge и публикаций сохраняются. Норма нового этапа предварительно 1 рабочий день до утверждения; подробности ROLES_WORKFLOW.md.

## 02.11.2026 — Тип документа и комплект договора: принято и реализовано
- Явный выбор пользователя TU / ACT_TP / AVTU. Автоматическая классификация содержимого пока отсутствует и не подменяет выбор. Предоставленная пара ТУ/АВТУ изучена локально, не загружается в синтетическую БД.
- Вместо отдельного обязательного маршрута АВТУ выбран прежний полный маршрут выбранного акта. ТУ — справочное приложение. Запрет на два вида за всю историю договора не вводится; для смены вида после первой версии нужна новая карточка act_id.
- Договор группируется по РЭС, строковому ключу номера и дате; нормализуются пробелы/NBSP и типографские дефисы, сохраняются нули/суффиксы. Разные даты и области не сливаются; будущий внешний API обязан обработать неоднозначность. Исходная строка номера остаётся в карточке.
- Выбор ТУ хранится у подготавливаемого акта, неизменяемый снимок ссылки — в cycles при отправке. Альтернатива привязки только при загрузке версии акта отвергнута: РИРУ должен иметь возможность загрузить ТУ после DOCX акта, но до отправки. Старым циклам неизвестная привязка не назначается задним числом.
- Новые таблицы RLS FORCE, runtime без UPDATE/DELETE редакций ТУ/договоров; собственные номера документов отделены от общего номера договора. Автоматического признания соответствия ТУ нет.

## 02.11.2026 — Принято: выбор типа файла РИРУ и альтернативные акты
Прямое уточнение пользователя: тип загрузки выбирается явно из ТУ / Акт ТП / АВТУ. ТУ связывается с выбранным видом акта по договору, оба вида актов одновременно не обязательны. Не реализовывать два обязательных последовательных акта или их общий обязательный пакет. Автоопределение типа может помогать, но не молча менять выбор. Исторические версии и ID не схлопываются. Selector/типизированный API пока не реализованы; это принятое требование к следующему этапу.

## 02.11.2026 — Уточнение пользователя: деловой ключ договора и типы документов
Номер договора ТП — общий ключ комплекта ТУ/АВТУ/акта ТП и будущего поиска для учёта ПУ. Внутренние UUID документов/версий/циклов и собственные номера сохраняются, одинаковый договор не заменяет act_id. АВТУ — самостоятельный тип, не синоним акта ТП. Это принятое предметное уточнение, не выполненная миграция/загрузка. Извлечение и числовую сверку сначала строить детерминированно с единицами, контекстом и источниками; текстовая близость точки не равна тождеству физической границы. Слабое/неоднозначное сопоставление требует ручной проверки. Маршрут АВТУ/пакета пока не задан, утверждённый workflow не менять. Реальные примеры/результаты остаются вне Git; детали CONTRACT_DOCUMENTS.md.

## 01.11.2026 — Принято: очередь → единое рабочее место
Основание — прямое задание пользователя по упрощению эксплуатации. Основная навигация: персональная очередь, отдельные действующие публикации, подготовка для РИРУ; общий рабочий список только вторичен. Альтернатива единого смешанного реестра с восемью действиями отвергнута из-за лишних переходов и неоднозначных выборок. Включение в approved задаёт реальная CURRENT/UNDER_REVISION публикация; новая редакция не подменяет скачиваемую утверждённую. Hash URL выбран для прямых ссылок без дополнительной настройки серверного rewrite; auth/RLS заново проверяются после F5. Фильтры/page/scroll разделены по пользователю и разделу. Основная дата — contract_date, новый явный dateField сохраняет совместимость со старым created_at API. Решение только в документе, явный versionId дополнительно проверяется внутри заблокированной команды, маршруты не меняются. COLLECTION/RETURNED и overdue разделены как состояние/признак, без изменения workflow. Правила renderer, неизменности источников и согласования прежние. REGISTRY_UI.md — актуальная спецификация.

## 01.11.2026 — Прототип DOCX без обещания точной вёрстки
ONLYOFFICE остаётся кандидатом: runtime не найден, Automation API требует Developer и отдельной оплаты по официальной документации. Не установлены системные службы/не куплена лицензия/не выполнены callback и fidelity-тесты. Для проверки версии/якорей реализован явно экспериментальный docx-preview 0.3.7: локальный sandbox iframe, DOMPurify, без прав на изменение оригинала. Это не одобренная промышленная замена ONLYOFFICE. БД хранит отдельный версионный anchor (file/block hash, part/paragraph, точный диапазон/цитата); сервер сверяет его с исходным OOXML. Неоднозначные абзацы fail-closed, на новую версию ничего не переносится автоматически. Сравнение только текста/снимков, не вёрстки. Текущие собственные визуальные замечания требуют RETURN, иначе специалист мог бы утвердить свою же неустранённую ошибку; маршруты/назначения/параллельность прежние. Браузерная печать карточки отключена по новой задаче пользователя; кнопки DOCX-печати disabled до надёжного генератора. Документы не передаются внешним сервисам. См. DOCX_PROTOTYPE.md.

## 01.11.2026 — Реестр и хронология как производные чтения
Статусы/маршрут/доступность действий выводятся SQL из существующих acts/cycles/tasks/decisions/comments/releases с RLS, без отдельной таблицы состояния UI. Альтернатива — клиентская агрегация всех карточек — отвергнута из-за N+1, неверных сводок/пагинации и лишней передачи данных. Новый GET registry фильтрует и считает сводки сервером. Карточка читает прежние записи плюс presentation/timeline в repeatable-read read-only snapshot; команды не менялись. Индексы и actor_snapshot аудита — миграция 006. История решений использует неизменное actor_name, новые audit-события сохраняют личность при записи; неизвестное прошлое имя не подменяется утверждением исторической точности. Timeline объединяет источники и не дублирует audit-решения. Браузерная печать явно обозначена как печать карточки; генерация пакета остаётся отдельной функцией. См. REGISTRY_UI.md.

| ADR-013 | Требование + механизм предложен | Внешний API только approved_release, service JWT, scope/РЭС/квоты | Чтение текущей карточки может раскрыть черновик; финальный формат ждёт изучения импорта ПУ |
| ADR-014 | Требование | ИИ только помощник; без внешней передачи ПДн и без автоматического согласования | OCR/правила и ручная проверка остаются необходимыми; локальный ИИ ещё не выбран |
| ADR-015 | Утверждено | TECH_ADMIN управляет пользователями/ролями без доступа к содержимому; PROCESS_ADMIN — процессом в своей области | Ни один не согласует вместо бизнес-роли |

## Утверждение и реализация ядра, 31.10.2026
- ADR-002/003/004/007/009/010/012 приняты пользователем как часть архитектуры; ONLYOFFICE (ADR-008) остаётся условным кандидатом до реальных DOCX и проверки API/лицензии.
- Новые правила пользователя: временное замещение по датам, подтверждение исправления автором, предварительные сроки 1/2/2/2/2 рабочих дня, пересмотр с полным циклом и сохранением прежней публикации.
- Публикации: CURRENT, UNDER_REVISION, SUPERSEDED, REVOKED. Пересмотр не равен автоматическому отзыву; будущий контракт ПУ должен учитывать статус явно.
- Реализация минимального назначения: один однозначный эффективный исполнитель; несколько кандидатов дают ошибку настройки, без произвольного выбора.
- Временная трактовка сроков ядра: N рабочих дат после поступления, сохраняется московское время, календарь полностью явный. Рабочие часы/первый день требуется уточнить до эксплуатации; праздники не генерируются как обычные выходные.
- Локальный приватный файловый адаптер для dev, production требует ClamAV; S3 и антивирус не проверены живым сервисом. Никакого production bypass авторизации.
- Тесты используют нативный PostgreSQL 17.11, закреплённый embedded-postgres@17.11.0-beta.19; бинарники PostgreSQL 18 падали 0xC0000005 на данном Windows. Бинарники/кластер запускаются в temp, процессы скрыты, БД останавливается после теста.
- Договорные поля пока в acts/version snapshot; отдельные contracts/connection points и service API остаются этапом 5. Python/ONLYOFFICE не имитируются заглушками, их функций в текущем ядре нет.

## Локальный стенд и браузерная проверка — 31.10.2026
- По прямой задаче пользователя добавлен отдельный dev-only launcher, который не принимает DATABASE_URL и не использует существующие базы; нативный PostgreSQL слушает 127.0.0.1:55432, база tp_approval_demo, cluster в системном temp и marker TP_APPROVAL_SYNTHETIC_ONLY.
- Вместо боевого Keycloak — явно обозначенный loopback JWT-сервис с собственным issuer/audience и RS256/JWKS. Backend использует штатный verifier без mock/injection. Вход без пароля разрешён только синтетическим пользователям локального стенда. Production launcher и настройки приложения этот сервис автоматически не включают.
- .local содержит ключи, пароли, документы, логи и браузерные артефакты и исключён из Git. Трассы с Authorization не публикуются; сохранены только screenshots/безопасный JSON-отчёт.
- Playwright запускает отдельный headless Chrome, не подключается к открытому профилю пользователя. Проверка 16 групп выполнена на Chrome 156.0.8078.48; отдельно проверено сохранение после остановки/повторного запуска всех четырёх сервисов.
- При интенсивном повторном сценарии обнаружен HTTP 429 от лишних UI-запросов. Открытие карточки теперь только читает её; после изменения обновляются динамические списки, профиль/РЭС загружаются при входе. Лимиты не отключены; ответы 429 структурированы и понятны пользователю.
- Учебные DOCX генерируются python-docx, офисный Word GUI и ONLYOFFICE не проверялись. Календарь учебный: явно помеченные будни, не официальный календарь РФ.

## Матрица согласования — 31.10.2026
- Матрица реализована как read-only derivation существующих таблиц, без дублирования статусов. Один SQL statement даёт согласованную snapshot при конкурирующих решениях; app.can_read/RLS действуют также на имена сотрудников.
- Снимки личности и защита закрытых задач добавлены миграцией 005, поскольку текущий профиль/истёкшее замещение не должны менять историческую строку. Сохранённый decisions.actor_name имеет приоритет. Legacy без решения не может быть достоверно восстановлен и явно помечен.
- Обновление — polling 5 секунд только видимой вкладки плюс focus/visibilitychange; WebSocket/SSE не вводился. Выбор цикла/вкладки — sessionStorage, не хранилище документов/JWT.
- Отсутствие решения показано отдельно серым, не как согласование. Итог выбранного цикла учитывает REVOKED publication, APPROVED cycle, активную просрочку и возврат; при возврате+просрочке отображаются оба признака. Норматив из версии политики задачи, длительность календарная до решения/закрытия, не выдуманное рабочее время.
- Маршруты команд, уведомления, badge и бизнес-решения не менялись. Ограничения и все проверки — docs/APPROVAL_MATRIX.md.

Это обосновывает разделение migration/runtime ролей; ссылка на 17 — источник механизма, не окончательный выбор версии БД.
