# Архитектурные решения

## 01.11.2026 — Прототип DOCX без обещания точной вёрстки
ONLYOFFICE остаётся кандидатом: runtime не найден, Automation API требует Developer и отдельной оплаты по официальной документации. Не установлены системные службы/не куплена лицензия/не выполнены callback и fidelity-тесты. Для проверки версии/якорей реализован явно экспериментальный docx-preview 0.3.7: локальный sandbox iframe, DOMPurify, без прав на изменение оригинала. Это не одобренная промышленная замена ONLYOFFICE. БД хранит отдельный версионный anchor (file/block hash, part/paragraph, точный диапазон/цитата); сервер сверяет его с исходным OOXML. Неоднозначные абзацы fail-closed, на новую версию ничего не переносится автоматически. Сравнение только текста/снимков, не вёрстки. Текущие собственные визуальные замечания требуют RETURN, иначе специалист мог бы утвердить свою же неустранённую ошибку; маршруты/назначения/параллельность прежние. Браузерная печать карточки отключена по новой задаче пользователя; кнопки DOCX-печати disabled до надёжного генератора. Документы не передаются внешним сервисам. См. DOCX_PROTOTYPE.md.

## 01.11.2026 — Реестр и хронология как производные чтения
Статусы/маршрут/доступность действий выводятся SQL из существующих acts/cycles/tasks/decisions/comments/releases с RLS, без отдельной таблицы состояния UI. Альтернатива — клиентская агрегация всех карточек — отвергнута из-за N+1, неверных сводок/пагинации и лишней передачи данных. Новый GET registry фильтрует и считает сводки сервером. Карточка читает прежние записи плюс presentation/timeline в repeatable-read read-only snapshot; команды не менялись. Индексы и actor_snapshot аудита — миграция 006. История решений использует неизменное actor_name, новые audit-события сохраняют личность при записи; неизвестное прошлое имя не подменяется утверждением исторической точности. Timeline объединяет источники и не дублирует audit-решения. Браузерная печать явно обозначена как печать карточки; генерация пакета остаётся отдельной функцией. См. REGISTRY_UI.md.

Дата первой записи: 31.10.2026. Статусы: «Требование» — задано пользователем; «Предложено» — ожидает утверждения; «Условно предложено» — дополнительно нужен прототип. Архитектура утверждена пользователем 31.10.2026 с уточнениями ниже; прежние статусы таблицы отражают исходное предложение, а новые записи имеют приоритет.

## Утверждение и реализация ядра, 31.10.2026
- ADR-002/003/004/007/009/010/012 приняты пользователем как часть архитектуры; ONLYOFFICE (ADR-008) остаётся условным кандидатом до реальных DOCX и проверки API/лицензии.
- Новые правила пользователя: временное замещение по датам, подтверждение исправления автором, предварительные сроки 1/2/2/2/2 рабочих дня, пересмотр с полным циклом и сохранением прежней публикации.
- Публикации: CURRENT, UNDER_REVISION, SUPERSEDED, REVOKED. Пересмотр не равен автоматическому отзыву; будущий контракт ПУ должен учитывать статус явно.
- Реализация минимального назначения: один однозначный эффективный исполнитель; несколько кандидатов дают ошибку настройки, без произвольного выбора.
- Временная трактовка сроков ядра: N рабочих дат после поступления, сохраняется московское время, календарь полностью явный. Рабочие часы/первый день требуется уточнить до эксплуатации; праздники не генерируются как обычные выходные.
- Локальный приватный файловый адаптер для dev, production требует ClamAV; S3 и антивирус не проверены живым сервисом. Никакого production bypass авторизации.
- Тесты используют нативный PostgreSQL 17.11, закреплённый embedded-postgres@17.11.0-beta.19; бинарники PostgreSQL 18 падали 0xC0000005 на данном Windows. Бинарники/кластер запускаются в temp, процессы скрыты, БД останавливается после теста.
- Договорные поля пока в acts/version snapshot; отдельные contracts/connection points и service API остаются этапом 5. Python/ONLYOFFICE не имитируются заглушками, их функций в текущем ядре нет.

## Локальный стенд и браузерная проверка — 31.10.2026
- По прямой задаче пользователя добавлен отдельный dev-only launcher, который не принимает DATABASE_URL и не использует существующие базы; нативный PostgreSQL слушает 127.0.0.1:55432, база tp_approval_demo, cluster в системном temp и marker TP_APPROVAL_SYNTHETIC_ONLY.
- Вместо боевого Keycloak — явно обозначенный loopback JWT-сервис с собственным issuer/audience и RS256/JWKS. Backend использует штатный verifier без mock/injection. Вход без пароля разрешён только синтетическим пользователям локального стенда. Production launcher и настройки приложения этот сервис автоматически не включают.
- .local содержит ключи, пароли, документы, логи и браузерные артефакты и исключён из Git. Трассы с Authorization не публикуются; сохранены только screenshots/безопасный JSON-отчёт.
- Playwright запускает отдельный headless Chrome, не подключается к открытому профилю пользователя. Проверка 16 групп выполнена на Chrome 156.0.8078.48; отдельно проверено сохранение после остановки/повторного запуска всех четырёх сервисов.
- При интенсивном повторном сценарии обнаружен HTTP 429 от лишних UI-запросов. Открытие карточки теперь только читает её; после изменения обновляются динамические списки, профиль/РЭС загружаются при входе. Лимиты не отключены; ответы 429 структурированы и понятны пользователю.
- Учебные DOCX генерируются python-docx, офисный Word GUI и ONLYOFFICE не проверялись. Календарь учебный: явно помеченные будни, не официальный календарь РФ.

## Источники механизмов

## Матрица согласования — 31.10.2026
- Матрица реализована как read-only derivation существующих таблиц, без дублирования статусов. Один SQL statement даёт согласованную snapshot при конкурирующих решениях; app.can_read/RLS действуют также на имена сотрудников.
- Снимки личности и защита закрытых задач добавлены миграцией 005, поскольку текущий профиль/истёкшее замещение не должны менять историческую строку. Сохранённый decisions.actor_name имеет приоритет. Legacy без решения не может быть достоверно восстановлен и явно помечен.
- Обновление — polling 5 секунд только видимой вкладки плюс focus/visibilitychange; WebSocket/SSE не вводился. Выбор цикла/вкладки — sessionStorage, не хранилище документов/JWT.
- Отсутствие решения показано отдельно серым, не как согласование. Итог выбранного цикла учитывает REVOKED publication, APPROVED cycle, активную просрочку и возврат; при возврате+просрочке отображаются оба признака. Норматив из версии политики задачи, длительность календарная до решения/закрытия, не выдуманное рабочее время.
- Маршруты команд, уведомления, badge и бизнес-решения не менялись. Ограничения и все проверки — docs/APPROVAL_MATRIX.md.

## Источники
- [PostgreSQL RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html): default deny при включённом RLS без политик; владельцы обычно обходят RLS, superuser/BYPASSRLS обходят всегда. Это обосновывает разделение migration/runtime ролей; ссылка на 17 — источник механизма, не окончательный выбор версии БД.
- [ONLYOFFICE permissions](https://api.onlyoffice.com/docs/docs-api/usage-api/config/document/permissions): возможно разрешить комментарии без редактирования; это не заменяет серверные права и проверку выбранной редакции API.
- [ONLYOFFICE security](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/security): отдельная подпись конфигурации и межсервисных сообщений JWT.
- [ONLYOFFICE callback](https://api.onlyoffice.com/docs/docs-api/usage-api/callback-handler): сохранение результата требует обработчика со стороны интегратора. Наличие API не доказывает корректность будущего моста замечаний TP_Approval.
