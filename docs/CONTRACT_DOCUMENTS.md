# Договор, ТУ, АВТУ и акт ТП

Уточнение ролей 02.11.2026: загружает и исправляет Инженер РИРУ своего РЭС; первым согласует отдельный Начальник РИРУ, затем Начальник РЭС, далее СТП/СУЭ/ТЕХБЛОК. Это относится к акту ТП и АВТУ. ТУ остаётся справочным приложением без отдельного маршрута. Подробности ROLES_WORKFLOW.md; прежнее краткое описание маршрута ниже историческое.

## Реализовано 02.11.2026
РИРУ явно выбирает тип файла: «ТУ», «Акт ТП» или «АВТУ». АВТУ и акт ТП — альтернативные виды акта, не два обязательных последовательных этапа. Выбранный акт проходит существующий маршрут: начальник РЭС, затем независимые СУЭ/СТП/ГИ, сбор всех решений, доработка и полный новый цикл. ТУ — справочное приложение; загрузка не создаёт согласование/версию акта. Отсутствие ТУ не превращено в новое блокирующее условие submit.

### Деловой идентификатор и группировка
Номер договора хранится строкой, с начальными нулями и суффиксами. Внутренние UUID договоров, актов, файлов, версий и циклов сохраняются. Таблица contracts объединяет только совпадающие РЭС + нормализованный номер + дату договора. Нормализация убирает пробелы/NBSP и приводит типографские дефисы к обычному; исходная строка номера договора не переписывается. Разные даты/РЭС не сливаются, несколько актов одного договора не схлопываются в одну карточку.

Собственные номера актов и ТУ хранятся отдельно от номера договора. Файлы скачиваются с именами «ТУ / АВТУ / Акт ТП к договору № … — редакция …». Это имя выгрузки, не изменение текста/байтов DOCX. Сервисный поиск для учёта ПУ предстоит реализовать: он должен учитывать неоднозначность, несколько точек и выдавать только актуальные утверждённые публикации по существующей политике.

### Модель и история
Миграция 009 добавляет contracts, technical_conditions, acts.contract_id/act_type/technical_conditions_id, cycles.technical_conditions_id, files.kind AVTU_DOCX. Существующие акты получают ACT_TP и договор; исторические циклы не получают выдуманную ссылку ТУ.
Редакции ТУ неизменяемы для runtime: собственные номер/дата, номер редакции внутри договора, файл, автор/дата загрузки. Нумерация защищена транзакционной блокировкой договора и уникальным ключом. RLS FORCE обеих таблиц сохраняет область РЭС; TECH_ADMIN не получает содержание. В цикле ссылка ТУ фиксируется на submit триггером и больше не меняется, даже если РИРУ позже загрузит другие ТУ.
В подготовке можно выбрать другую уже загруженную редакцию ТУ того же договора. Загрузка выбирает новую редакцию только для текущего акта, не переписывает другие карточки. На review/APPROVED менять приложение нельзя. После первой версии вид акта фиксирован; для другого вида нужна отдельная карточка того же договора. Это не запрет исторических актов другого вида по договору.
API и триггер БД запрещают использовать ТУ или файл другого вида как версию акта. Предыдущие замечания/решения/якоря/замещение/запрет самосогласования/персональный badge сохраняются.

### Пользовательский сценарий
1. Войти РИРУ, открыть «Подготовка актов», создать карточку с номером и датой договора и отдельным номером акта.
2. В рабочем месте выбрать «ТУ», указать собственные номер/дату ТУ при наличии, загрузить DOCX.
3. В свёрнутой панели «ТУ и документы договора» доступны редакции, просмотр и скачивание; договор виден отдельно от собственных реквизитов.
4. Выбрать «АВТУ» либо «Акт ТП» и загрузить DOCX выбранного акта. Создаётся первая версия, появляется отправка на согласование.
5. Отправить акт. Цикл сохраняет использованную редакцию ТУ. При возврате исправить акт во внешнем Word, загрузить новый DOCX того же вида, указать исправления и повторно отправить.
6. Для новой редакции ТУ на доработке выбрать «ТУ» и загрузить файл либо выбрать уже существующие ТУ договора. Старый цикл продолжает ссылаться на прежние ТУ.

## Проверка и ограничения
Созданы синтетические tu-v1.docx/avtu-v1.docx с таблицей, объединениями, колонтитулами и разрывом страницы (scripts/create-document-fixtures.py). Новые тесты: tests/contract-documents.integration.ts, contract-documents.browser.ts, contract-documents-persistence.ts. Команды и фактические результаты — PROGRESS.md и LOCAL_BROWSER_GUIDE.md.
- Пока только DOCX. PDF/сканы явно не поддерживаются загрузкой; OCR нет.
- Просмотр приблизительный docx-preview, не точная вёрстка Word. Нет редактирования исходного DOCX в браузере, точной печати и ONLYOFFICE.
- Тип выбирает человек; автоматического определения/проверки типа и извлечения номера договора из текста при загрузке пока нет. Метаданные карточки требуют проверки пользователем.
- Отдельного общего экрана реестра договоров пока нет: комплект представлен в рабочем месте акта.
- Нет промышленного отчёта сверки ТУ ↔ акт и внешнего API учёта ПУ. Нельзя считать факт прикрепления ТУ подтверждением соответствия.

## Локальное исследование предоставленных примеров
До реализации изучены два реальных DOCX: ТУ и АВТУ. Отдельного акта ТП в примерах нет. Исходники не изменялись, в синтетическую БД/публичный Git/внешние AI API не переносились. Скрипты и результат с цитатами/OOXML-местами находятся только в игнорируемой .local/sample-review; вся папка примеров исключена из Git.
Разовый Python/XML/Decimal-прототип без ИИ сопоставил номер договора, адрес/кадастровый номер, полную/существующую/дополнительную мощность, напряжение с приведением единиц, обозначение ТП и питающий центр. Собственный номер ТУ отличается от договора. Совпадение компонентов точки не доказывает эквивалентность физических контактов/границы: требуется ручная проверка. Категория надёжности может указывать увеличение вместо полной мощности; подозрительные единицы и неподтверждённая дата ТУ не исправляются автоматически.

## Следующий этап — детерминированная сверка
Нужен производственный извлекатель реквизитов по типам/контексту и исходным OOXML-якорям; нельзя брать первое число с единицей во всём документе. Мощности: всего, ранее присоединённая, увеличение, генерация и распределение по точкам отдельно. Сравнение чисел Decimal после приведения единиц; адреса по компонентам, кадастровый номер отдельно. Точка присоединения: устройство, напряжение, код ТП, мощность и описание границы — разные поля.
Каждый вывод MATCH / DIFFERENCE / UNKNOWN / MANUAL_REVIEW должен содержать обе цитаты, версии и местоположения, применённое правило. Отсутствие не равно нулю/совпадению. Автоматическая проверка не принимает решение о согласовании. Потребуется дополнительный пример акта ТП и обезличенные шаблоны/искажения для тестирования. Универсальный импорт DOCX/PDF/сканов не считается выполненным по двум образцам.
