# TP_Approval — задания для Codex: пакет документов, визуализация, правки, печать

Подготовлено 03.11.2026 по состоянию `main` = `d6c6adf`.

## Как пользоваться

1. Положите в репозиторий и закоммитьте папки из этого комплекта:
   - `docs/design/target-ui.html` — эталонный макет (откройте в браузере, экраны переключаются вверху);
   - `docs/design/target-*.png` — снимки макета;
   - `docs/codex/CODEX_PROMPTS.md` — этот файл.
2. Отдавайте Codex **по одному этапу** — отдельной задачей. В начало каждой задачи вставляйте блок «Общая часть» (раздел 0) и затем текст этапа целиком.
3. После каждого этапа откройте стенд (`npm run demo`) и посмотрите результат сами. Следующий этап — только после приёмки предыдущего.
4. Порядок важен: 1 → 2 → 3 → 4 → 5 → 6. Этап 2 (сверка) идёт раньше мастера создания, потому что мастер показывает её результат.
5. Блок «Решения пользователя» в разделе 0 — это бизнес-правила, которые Codex по `AGENTS.md` не вправе менять сам. Прочитайте их: вставляя блок в задание, вы их утверждаете. Если с чем-то не согласны — исправьте текст до отправки.

## Этап 2. Сверка АВТУ/АКТ ТП с ТУ на реальном шаблоне и ручное подтверждение

```text
ЦЕЛЬ
Реальный комплект «ТУ + АВТУ» Россети Юг должен проходить сверку: совпадающие
реквизиты — MATCH, спорные — на ручное подтверждение инженером (решение Р4),
расхождения — блокируют отправку. Сейчас реальный комплект отправить невозможно.

ФАКТ (проверено локально прогоном apps/api/src/tu-rules.ts, DOCX_CONTEXT_V3,
на реальной паре ТУ + АВТУ одного договора; значения ПДн здесь не приводятся)
  Номер договора        MATCH
  Максимальная мощность UNKNOWN  — в АВТУ «15,0 (пятнадцать) кВт» не читается:
                                    слово в скобках между числом и единицей; зато в
                                    кандидаты «всего» попали 8,0 кВт (см. ниже) и
                                    7,0 кВт из «ранее присоединенная максимальная
                                    мощность» (квалификатор стоит ДО совпадения и не
                                    проверяется); 15,0 из таблицы не читается
  Класс напряжения      UNKNOWN  — в АВТУ значение «0,4» в ячейке таблицы, единица
                                    только в заголовке колонки «Уровень напряжения (кВ)»
  Адрес                 MANUAL_REVIEW — в АВТУ «по адресу:» в п.5 тянет хвост
                                    «…, сетевой организацией в лице электромонтёра …»
  Точка присоединения   UNKNOWN  — в АВТУ точка в ячейке таблицы «Описание точки
                                    присоединения»
  → отправка заблокирована, ручного обхода нет.

Ошибка V3 по мощности: в абзаце «максимальная мощность (без учета ранее
присоединенной (существующей) максимальной мощности) 8,0 кВт» регулярное выражение
находит второе совпадение «максимальной мощности» внутри скобок; хвост первого
```

```text
   замечания), «Комментарий». Хранение — существующие поля comments.original_value /
   suggested_value / discussion; «правка» = suggested_value не пусто. Миграция не нужна.
3. Отображение в тексте (DocumentViewer), только для привязок к хешу текущего файла:
   - замечание: подчёркивание 2px + заливка, номер в кружке после фрагмента;
   - правка: исходный фрагмент зачёркнут, сразу после него вставлен правильный текст
     (подчёркнут), номер в кружке;
   - цвет по статусу: открыто/отклонено — красный, исправлено и ждёт автора — янтарный,
     подтверждено — зелёный; плюс текстовый статус в подсказке и карточке;
   - на правом поле страницы — кружок с инициалами автора на уровне абзаца; клик →
     карточка в панели; подсказка: ФИО, роль, вид ошибки, дата, статус;
   - флажок «Показать правки и замечания» (по умолчанию включён).
   Вставленный текст правки — элемент-наложение (data-overlay, contenteditable=false,
   user-select:none). Расчёт смещений выделения и поиск должны игнорировать
   наложения, иначе сломаются привязки. Покрыть тестом.
4. Замечания видят все, кто может читать документ (это уже обеспечивает RLS).
   В панели — все циклы с фильтрами; в каждой карточке — цепочка событий из
   comment_events: «<ФИО> исправил(а) в версии N, дата: пояснение», «<ФИО> подтвердил
   устранение», «<ФИО> отклонил исправление».
5. «Сравнить с версией N» — наложение на текст новой версии: удалённые слова
   красным зачёркнутым, добавленные — красным подчёркнутым; вверху строка «Изменения
   версии 2 относительно версии 1 — внесла <ФИО>, <дата>». Сервер: расширь
   GET /compare, чтобы он возвращал изменения по абзацам новой версии (blockId + операции
   diffWordsWithSpace); сопоставление абзацев — по порядку с LCS по тексту.
   Помечай результат как приблизительный в подсказке. Без перезаписи исходников.
6. «Применить правки» (инженер, акт RETURNED/REVISING, открыта последняя версия):
   список правок к последней версии в статусе OPEN/REOPENED с флажками →
   POST /api/v1/acts/:id/apply-corrections {versionId, commentIds[], expectedRevision},
   Idempotency-Key. Сервер:
   - берёт байты последней версии, проверяет каждую привязку checkAnchor;
   - пересекающиеся привязки → 409 с перечнем;
   - в нужной части (document/header/footer) заменяет диапазон [start, end) текста
     абзаца на правильный текст: разрезает runs по границам, новый текст получает
     w:rPr первого затронутого run, учитывает w:tab/w:br; остальные абзацы и все
     прочие части ZIP — побайтно без изменений (тест);
   - результат проходит validateDocx и сохраняется новой версией существующим кодом
     создания версии (автор — инженер);
   - по каждой применённой правке добавляет событие REPORTED_FIXED с пояснением
     «Правка применена в версии N» (действует инженер).
   Дальше всё как сейчас: сверка → отправка → полный цикл → автор подтверждает.
   Ручная загрузка исправленного DOCX остаётся.
7. «Скачать с исправлениями для Word»: для версии, созданной применением правок,
   производный DOCX (не версия, не согласуемый файл), где применённые изменения
   записаны рецензированием Word: w:del/w:ins с w:author = «<ФИО> (<роль>)» автора
   правки и w:date = время правки. В Word они видны красным с автором. Аудит
   скачивания. Согласуется по-прежнему чистая версия.

НЕ ДЕЛАТЬ
- Не давать согласующим менять файл версии. Не переносить привязки на новую версию
  эвристически (AGENTS.md): на новой версии старые замечания показываются в панели,
  а в тексте — только при совпадении хеша файла.
- python-docx и пересохранение всего документа не использовать: правка только
  затронутых абзацев.

ПРОВЕРКИ
Unit: замена через 3 runs, tab/br, колонтитул, неизменность прочих частей,
пересечения, w:ins/w:del. Integration: права (согласующий 403, чужой РЭС 404),
устаревший expectedRevision 409, повтор по ключу, события REPORTED_FIXED, далее
полный цикл с подтверждением автором. Browser: выделение → правка → видна у
другого пользователя с правильным автором/цветом → возврат → инженер применяет →
v2 → сравнение показывает изменения → автор подтверждает → зелёный цвет.
Регрессия test:documents:browser, test:riru:browser, test:browser; persistence
test:documents:persistence.

ДОКУМЕНТЫ
docs/DOCX_PROTOTYPE.md (правки, наложения, применение, рецензирование Word),
docs/ROLES_WORKFLOW.md (кто что может с правками).
```

## Этап 5. Печать пакета: лист согласования и лист замечаний

```text
ЦЕЛЬ (Р6)
После полного согласования — «Печать пакета»: утверждённый документ без изменений,
лист согласования, лист замечаний со всеми замечаниями всех циклов. Экран 4 макета.

ЧТО СДЕЛАТЬ
1. Доступно, только если у акта есть публикация CURRENT или UNDER_REVISION;
   используются её версия и цикл. Иначе 409. Права и RLS — как на скачивание.
2. Данные листа согласования: отправка инженером (ФИО, время), решения всех этапов
   утверждённого цикла (роль, ФИО-снимок, решение, время, «по замещению» если было),
   число замечаний каждого участника за все циклы, итог: дата согласования, число
   циклов, число замечаний и сколько устранено. Источник — те же данные, что у
   matrix.ts / timeline.ts, без новых копий статусов.
3. Лист замечаний: все комментарии акта по всем версиям и циклам: №, цикл/версия,
   автор и роль, вид ошибки, «было → стало» (или текст замечания), как устранено
   (версия, кто подтвердил, когда). Если замечаний не было — «Согласовано без замечаний».
4. Форматы:
   a) HTML-страница печати #/acts/:id/print: A4, @media print, повтор шапки таблиц,
      разрывы страниц; «Печать листов» → window.print().
   b) DOCX «Лист согласования» — генерация на сервере из минимального OOXML-шаблона
      через jszip (уже есть в зависимостях): Times New Roman, таблицы с явными
      границами, только прямое форматирование.
   c) Сводный DOCX «<договор> <вид акта> + лист согласования.docx»: копия
      утверждённого DOCX, в document.xml перед финальным w:sectPr — разрыв раздела
      (A4, книжная) и тело листов. Остальные части ZIP — побайтно без изменений,
      новые стили/нумерацию не добавлять. Результат проходит validateDocx. Если
      склейка не удалась — показать причину и дать скачать файлы по отдельности.
   Исходный файл версии не изменяется (проверка SHA-256 до/после).
   Внизу листа: «Сформировано <дата> по утверждённой версии N (SHA-256 …).
   Электронное согласование не является электронной подписью.»
5. Миграция: app.print_jobs(id, act_id, release_id, version_id, kind,
   template_version, source_sha256, output_sha256, file_id, status, error,
   created_by, created_at), RLS, файлы приватные, аудит.
6. Кнопки: «Печать пакета» в шапке согласованного документа и в строке реестра
   раздела «Согласованные».
7. Обнови AGENTS.md и docs: печать теперь = сводный DOCX и HTML-листы; HTML-просмотр
   docx-preview по-прежнему не печатается и остаётся приблизительным.

ПРОВЕРКИ
Integration: только утверждённые; чужой РЭС 404; замечания всех циклов, включая
устранённые; случай без замечаний; замещение отражено; исходный хеш не изменился;
DOCX валиден. Browser: печатная страница, вызов window.print (заглушка в тесте),
имена файлов, открытие сводного DOCX через DocumentViewer без ошибок.
Если локально доступен LibreOffice — дополнительно конвертация сводного DOCX в PDF
как проверка открываемости (не обязательная зависимость).
```
