## Что работает
- Вкладка «Матрица согласования»: четыре согласующих, версия/цикл и история, ФИО/замещение, сроки/длительность, цвет/текст/значки, счётчики замечаний, общий итог включая отзыв и явное отсутствие решения. RLS API и автообновление видимой вкладки раз в 5 секунд. См. [APPROVAL_MATRIX](APPROVAL_MATRIX.md); миграция 005 хранит только снимки личности, не новые копии статусов.
- Express 5 / TypeScript API, React/Vite интерфейс, сборка обоих приложений; package-lock фиксирует зависимости.
- Проверка RS256 JWT через JWKS: issuer/audience/exp/iat/sub и realm-роль tp-approval-user. Идентификация по (issuer,subject), без доверия email и без dev-token/bypass.
- Семь РЭС, роли RIRU_HEAD/RES_HEAD/SUE/STP/GI, TECH_ADMIN и PROCESS_ADMIN с областью РЭС. Runtime PostgreSQL не владелец таблиц, без BYPASSRLS/superuser; сервер отказывается запускаться с опасной ролью БД.
- SQL-миграции с журналом/checksum/advisory lock, транзакцией и отдельной runtime-ролью. Базовые справочники не содержат тестовых пользователей.
- Создание карточки, реестр, карточка с историей, DOCX upload и download. Исходные байты сохраняются; UUID-имена файлов вне web-root, SHA-256 проверяется при скачивании.
- Проверка DOCX ZIP/OOXML: число частей, размер, шифрование, внешние связи, макросы/activeX/вложения и DTD; production требует ClamAV. В dev без ClamAV выполняется **только структурная проверка**, это явно записывается в аудит. Для реальных файлов нужен антивирус.
- Версии со снимками реквизитов и JSON technicalData; UPDATE версий/решений/замечаний/аудита недоступен runtime. Редактирование текста Word внутри интерфейса отсутствует.
- РЭС → параллельно СУЭ/СТП/ГИ. RETURN сохраняет текстовое замечание и не отменяет проверки остальных. Доработка отдельной задачей; повторная подача только новой версии, с полным новым циклом.
- Блокировка акта/задачи, уникальные решения и активный цикл, идемпотентность команд с сохранением результата; устаревшая ревизия отклоняется.
- Запрет автору/создателю версии согласовывать свой акт; один человек не принимает решения в разных ролях по тому же акту, включая разные циклы. Повторное решение в той же роли нового цикла разрешено.
- Датированное замещение назначением PROCESS_ADMIN, без перекрытия интервалов. Задача связана с исходным назначением роли: эффективный исполнитель/badge меняются на время замещения и возвращаются после окончания. Первоначальный assignee и фактический автор решения сохраняются. Новое уведомление при самом начале замещения пока автоматически не создаётся.
- РИРУ сообщает об исправлении с версией/пояснением, автор замечания подтверждает в активной повторной задаче. События VERIFIED/REOPENED учитываются по последнему событию. Заместитель не получает права подтвердить за автора; если автор недоступен, нужен возврат/исключительная процедура, а не фиктивная отметка.
- Персональные задачи/просрочка, уведомления/read_at и независимый badge COUNT DISTINCT актов. Отметка прочтения не завершает задачу.
- Предварительные нормативы 1/2/2/2/2 рабочих дня; явный календарь с источником и ревизией, снимок использованных дней в задаче. Нет календаря/есть разрыв — 409 и полный rollback.
- PROCESS_ADMIN может закрыть центральный сбор, когда все оставшиеся OPEN задачи просрочены, с обязательной причиной. Они CANCELLED, без решений; создаётся задача доработки.
- POST /api/v1/admin/run-deadlines формирует WARNING за 4 календарных часа (предварительное значение), OVERDUE и ESCALATION процессным администраторам соответствующей области. События и уведомления дедуплицируются; журнал доступен через /acts/{id}/deadline-events. **Автоматический scheduler/доставка вне приложения ещё не запущены**: метод вызывается вручную; worker и настраиваемый список дополнительных адресатов — следующий этап.
- Пересмотр утверждённого акта, UNDER_REVISION, новый полный цикл, SUPERSEDED/CURRENT; отзыв PROCESS_ADMIN с причиной REVOKED. Предыдущая версия физически сохраняется.
- Аудит и outbox записываются в той же транзакции. Потребителя outbox/интеграции подробных уведомлений с оболочкой пока нет.

## Фактический API
Реализованные маршруты — в apps/api/src/app.ts. Пользовательские: /me, /res, /acts, /acts/{id}, /acts/{id}/files, /files/{id}/download, /acts/{id}/versions, /acts/{id}/submit, /tasks/mine, /tasks/{id}/decision, /comments/{id}/events, /notifications, /notifications/{id}/read, /platform/badge, /acts/{id}/revise, /releases/{id}/revoke, /acts/{id}/close-collection, /acts/{id}/deadline-events. Префикс /api/v1, кроме /api/platform/badge.

Администрирование API: /api/v1/admin/directory (GET), /users, /substitutions, /calendar, /deadline-policies, /run-deadlines (POST). Для всех POST JSON-команд нужен Idempotency-Key. Загрузка файлов — multipart без этого требования. Ошибки содержат requestId; чужие объекты 404, отсутствие роли 403, конфликт 409, устаревшая ревизия 412, валидация 422.

Внешний /api/v1/contracts/lookup **ещё не реализован**, service JWT/квоты/журнал интеграций — этап 5. Целевой контракт сохранён в API_CONTRACTS. Нельзя подключать учёт ПУ к текущим полям карточки вместо утверждённых публикаций.

## Локальный запуск

Для безопасной проверки **без боевого Keycloak** теперь есть `npm.cmd run demo`: frontend http://127.0.0.1:5173, API :3000, JWT/JWKS :4100, отдельный PostgreSQL :55432/tp_approval_demo. Девять пользователей выбираются на явно помеченном тестовом экране. Это отдельный launcher с синтетическими данными и реальной проверкой JWT, не production bypass. Полная инструкция и сценарий — [LOCAL_BROWSER_GUIDE](LOCAL_BROWSER_GUIDE.md). .env для него не нужен, существующие базы не используются. БД сохраняется при `npm.cmd run demo:stop` и повторном запуске.
Требуются Node.js >=22.18, npm, PostgreSQL 17 и действующий Keycloak. Docker Compose — альтернативный запуск PostgreSQL; на текущем компьютере Docker не найден, конфигурация Docker не проверялась запуском.

1. `npm.cmd ci` (PowerShell может блокировать npm.ps1, используйте npm.cmd).
2. Скопировать .env.example в .env и заполнить реальные локальные подключения/issuer/JWKS/audience/origin. Секреты не коммитить. Роль tp-approval-user и audience должны присутствовать в реальном токене; сервер не ослабляет проверку ради несовпадения конфигурации.
3. PostgreSQL создать отдельно либо выполнить `docker compose -f infra/compose.yaml up -d` с POSTGRES_PASSWORD в окружении. Это локальная команда; её здесь не выполняли.
4. `npm.cmd run db:migrate`. MIGRATION_DATABASE_URL должен принадлежать доверенному администратору БД с правом создания tp_runtime и SECURITY DEFINER функций; не использовать его в API. RUNTIME_DB_PASSWORD задаёт пароль отдельной runtime-роли. В минимальном setup миграции запускаются доверенным PostgreSQL superuser; production migration owner/гранты дополнительно проверить до выпуска.
5. Для первичного TECH_ADMIN задать BOOTSTRAP_ISSUER, BOOTSTRAP_SUBJECT (sub реального пользователя), BOOTSTRAP_NAME и выполнить `npm.cmd run db:bootstrap`. Этот скрипт не создаёт пароль и не изменяет Keycloak.
6. TECH_ADMIN через POST /api/v1/admin/users привязывает пользователей и выдаёт роли, включая PROCESS_ADMIN. Формат: issuer, subject, name, role, resId (null только для центральных/явно глобальных администраторов). Например RIRU_HEAD/RES_HEAD требуют UUID конкретного РЭС из /res. Нужен реальный JWT и Idempotency-Key.
7. PROCESS_ADMIN загружает /admin/calendar: {days:[{day:"2026-11-01",working:false,source:"Утверждённый календарь"},...]}. Нужны подряд все даты, включая выходные, на весь горизонт срока. Автозаполнения официальными праздниками нет. Предварительные нормативы уже в миграции.
8. `npm.cmd run dev:api`, в другом терминале `npm.cmd run dev:web`. Vite проксирует /api на 127.0.0.1:3000. Фронтенд читает VITE_PLATFORM_ORIGIN из корневого .env; этот origin должен совпадать с PLATFORM_ORIGIN сервера.
9. Войти через оболочку или передать действующий JWT в локальную форму входа. Он остаётся в памяти, не localStorage. В платформе реализован app-ready/platform-auth с проверкой origin/source и периодическим запросом нового токена. Реальный iframe/SSO ещё не проверен end-to-end; SUE_system не менялся.

Production: `npm.cmd run build`, затем `npm.cmd start` с переменными среды и WEB_PATH=dist/web. NODE_ENV=production требует HTTPS origins и CLAMAV_HOST, обхода авторизации нет. Dockerfile — заготовка воспроизводимой упаковки без развёртывания; VITE_PLATFORM_ORIGIN передавать build-arg. TLS/reverse proxy, секреты, резервное копирование и ресурсы надо проверить отдельно. Локальное файловое хранилище разрешено только как dev-адаптер; production S3-адаптер и backup/restore ещё не реализованы.

## Проверки и границы
- npm run build: типы и сборка API JS + frontend.
- npm test: 3 группы проверок DOCX/JWT/HTTP JWKS с негативными сценариями.
- npm run test:integration: 16 групп на настоящем PostgreSQL 17.11, реальном HTTP Express через supertest и подписанных синтетических RS256 JWT. Миграции применяются дважды для проверки повторного запуска.
- Изолированный тестовый cluster создаётся в системном temp, слушает только 127.0.0.1, получает случайные пароли и останавливается в finally. Windows-бинарники копируются в temp с ASCII-путём. Тестовые артефакты сохраняются для диагностики; реальные данные туда не попадают. PostgreSQL 18 из npm на этом Windows завершался 0xC0000005; проверенный тестовый пакет закреплён на 17.11.0-beta.19.
- Тесты в песочнице Windows блокировались на Node userInfo; успешно выполнены с разрешением вне песочницы. Это ограничение среды, не отключение проверок приложения.
- Реальная браузерная проверка выполнена headless Chrome/Playwright: 9 пользовательских сессий и 16 групп полного цикла, приватности, персональных сообщений/badge, сроков и mobile viewport. Дополнительно проверено восстановление состояния после перезапуска всех сервисов; отчёты .local/browser-report/result.json и restart-result.json. Реальный Keycloak/iframe SSO, ClamAV, Docker, реальные DOCX, Microsoft Word GUI и ONLYOFFICE не проверены. Python-сервис, ТУ/PDF, привязка к фрагментам, категории ошибок, печать, Excel, аналитика и внешний API ещё не реализованы. Расширенные фильтры/пагинация и UI администрирования также впереди; реестр ограничен 100 строками на запрос.

Браузерный цикл завершён на синтетическом стенде. Следующие шаги: административный UI/расширенные фильтры, загрузка ТУ, сканирование и storage, затем прототип ONLYOFFICE на разрешённых DOCX. Подключение реального Keycloak/платформы отложено по указанию пользователя; не объявлять production SSO или этапы 3–6 готовыми.
