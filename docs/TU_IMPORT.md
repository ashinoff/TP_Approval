# Создание документа из ТУ

Последнее уточнение 03.11.2026: на экране одна кнопка «Создать документ», форма открывается по нажатию; её действие — «Сохранить документ». Распознанного номера договора достаточно для сохранения пакета с выбранным актом; остальные неизвестные реквизиты необязательны. contract_date хранит NULL (миграция 013), сегодняшняя дата не выдумывается. Ниже прежнее описание ввода даты следует понимать как возможность, а не обязательное условие сохранения. Неизвестная дата отображается «Не указана». Отдельного редактора этих реквизитов после создания пока нет.

Для ТУ с локальной ссылкой attachedTemplate extract-tu возвращает preparedFile (base64 безопасной копии, originalSha256, removedTemplateLinks) и notice. UI явно сообщает о подготовке и использует копию при сохранении. Исходник на компьютере не меняется. prepare-tu.ts допускает только точный тип attachedTemplate в word/_rels/settings.xml.rels с file-ссылкой; удаляет связь и соответствующий узел settings.xml, проверяет остальные части побайтно и повторяет строгую валидацию. Любые другие внешние связи/удалённые шаблоны запрещены; подписанные пакеты с такой связью не преобразуются. Обычная загрузка файлов/проверка версий остаётся строгой, преобразование доступно только до импорта ТУ через эту форму. Точная Word-вёрстка этим не подтверждается.

Принято пользователем 03.11.2026: одно действие «Создать документ», номер нового документа равен номеру договора. Пакет содержит ТУ и альтернативно АКТ ТП либо АВТУ. Имена скачивания: `<номер договора> АВТУ.docx`, `<номер договора> АКТ ТП.docx`, `<номер договора> ТУ.docx`; начиная со второй редакции добавляется её номер. Байты исходных документов не переписываются.

Инженер выбирает вид акта и загружает ТУ DOCX. POST `/api/v1/documents/extract-tu` принимает multipart file/resId, проверяет JWT, роль инженера именно этого РЭС, структуру DOCX и антивирус согласно окружению. Разбор локальный, без ИИ и внешних сервисов. До создания файл разбирается в памяти, не публикуется и не сохраняется. Ответ: source=TU_DOCX, sha256, fields.contractNumber/applicant/address/contractDate с value и статусом FOUND/NOT_FOUND/AMBIGUOUS, limitations. Отсутствующие и неоднозначные поля пустые. Это предложения реквизитов, не положительный результат сверки ТУ.

Номер извлекается из «Приложение к договору № …», заявитель — из «Заявитель: …», адрес — из адресного пункта с переносами. Читаются абзацы Word, включая таблицы и разбиение на runs. Дата договора распознаётся только при явном `от ДД.ММ.ГГГГ` после номера в шапке. Дата создания показывается отдельно как текущая, в БД created_at назначается сервером. Дату договора нельзя подменять датой создания: при отсутствии её вводит инженер. Реквизиты проверяемы/редактируемы до сохранения.

После создания существующие API сохраняют карточку, редакцию ТУ и первую версию выбранного акта. При частичной ошибке повторная попытка использует уже созданную карточку; успешно загруженные файлы в рамках формы не повторяются. Открывается единое рабочее место со сверкой и отправкой по прежнему маршруту. Пустой черновик через новую форму больше не создаётся; прежний API создания карточек сохранён для совместимости.

Пакет использует существующие contracts/technical_conditions/acts/files/versions. Номер договора — деловой ключ, UUID — технические ключи. Область РЭС и дата договора по действующей схеме остаются частью идентичности contracts; разные существующие записи по одному номеру автоматически не объединяются. Разные act_id не схлопываются. Старые номера/версии/публикации не переписываются. Схема, ПСУ и предыдущий акт — будущие вложения, их загрузка ещё не реализована.

В рабочем месте открыт блок пакета с выбором «Документ пакета». Акт и ТУ переключаются без смены раздела; при просмотре ТУ скрываются действия решения и панель замечаний к акту. Серверный API замечаний по-прежнему требует версию акта и действующую задачу. ТУ цикла фиксируются при отправке, все редакции подписаны явно.

При переключении на ТУ DOM предпросмотра акта и формы замечания сохраняется скрытым: набранное замечание не теряется. Проверено в Chrome с настоящим выделением фрагмента, вводом черновика, переключением на ТУ и обратно. Права на создание/подтверждение замечаний и решения остаются прежними.

Ограничения: только DOCX; неизвестные шаблоны могут потребовать ручного заполнения. Автозаполнение не означает полную проверку правильности документа. Строгая сверка DOCX_CONTEXT_V3 не менялась. docx-preview остаётся приблизительным просмотром, редактирование Word/PDF/OCR и печать отсутствуют. Внешние связи DOCX отклоняются. Реальные примеры не загружались разработчиком в тестовую БД.
