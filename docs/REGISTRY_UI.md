## Путь согласующего
Вход → **На согласование** → клик по строке/ссылке договора → документ и замечания → **Согласовать** / **Вернуть с замечаниями** → короткое подтверждение с актом/версией/циклом. Решение закрывает персональную задачу, не весь маршрут. После возврата одной службы другие продолжают проверку. После завершения всех проверок документ либо возвращается РИРУ, либо публикуется.

Основное меню: «На согласование», «Согласованные», для РИРУ «Подготовка актов». «Все в работе» — вторичный переключатель возле персональной очереди. Уведомления открываются колокольчиком; unread не является числом задач. Счётчик платформы /api/platform/badge по-прежнему считает уникальные акты с любым персональным действием, включая доработку РИРУ. Поэтому badge может отличаться от счётчика очереди согласования.

## Реальные серверные выборки
GET /api/v1/registry дополнен view:
- queue: открытая эффективная задача текущего пользователя с ролью согласующего (не RIRU_HEAD), с учётом датированного замещения и app.has_role;
- work: все доступные акты в работе, а также не имеющие действующей публикации, включая черновики/доработку/отозванные;
- preparation: доступная область RIRU_HEAD, те же незавершённые акты. Автор карточки не является единственным пользователем, которому разрешена подготовка — сохраняются замещение и область роли;
- approved: существует реальная CURRENT или UNDER_REVISION публикация. SUPERSEDED/REVOKED исключены. При пересмотре старая утверждённая редакция остаётся доступна по принятой политике и явно помечается «на пересмотре».

GET /api/v1/registry-counts возвращает queue/work/preparation/approved по полной доступной выборке без пользовательских фильтров. Сводки возле списка соответствуют его активным фильтрам. Все запросы под прежним RLS, runtime без BYPASSRLS. act_id остаётся ключом строки/карточки; одинаковый договор не объединяет акты.

GET /api/v1/workspace-state объединяет те же задачи, уведомления, badge и счётчики в одном read-only repeatable-read запросе. Отдельные старые endpoints используют те же функции и сохраняют контракт. Это уменьшает фоновый HTTP-трафик без увеличения лимитов API (600/IP и 180/пользователь в минуту). Уведомления содержат номер акта/договора; возврат также содержит ссылку comment_id на сохранённое замечание на момент события.

approvedPublication содержит id/status/versionId/versionNumber/fileId/cycleId. Меню скачивания в «Согласованных» использует именно эту версию, даже при наличии нового черновика или незавершённого цикла. При status=APPROVED внутри view=approved фильтр проверяет публикацию; REVISING — UNDER_REVISION.

## Реестр и даты
Шесть колонок: РЭС, договор (акт второй строкой), **дата договора**, компактные индикаторы этапов, основной статус с отдельной просрочкой, действия. СУЭ/СТП/ГИ сгруппированы параллельно. В строке видны «Открыть» и «Ещё»; в меню — скачивание, история, матрица. Фиктивная печать отсутствует. Свободная область строки кликабельна; ссылка договора доступна с клавиатуры и имеет адрес act_id. Вложенное действие не открывает строку.

Постоянные условия: поиск, РЭС, статус, дата договора с/по. Остальное — «Дополнительные условия». Для однозначного собственного РЭС поле фиксировано; серверные проверки остаются обязательными.

UI всегда отправляет dateField=contract. Даты сравниваются включительно с acts.contract_date. Для совместимости прежний API без dateField сохраняет created_at с московскими границами суток (dateField=created); это не переименованная старая фильтрация. Поиск по прежним полям, technicalData и замечаниям сохранён.

## Карточка и навигация
Один документ с общей панелью замечаний. ActDocument теперь содержит только единственные controls загрузки/отправки РИРУ внутри WordWorkspace. Выбор решения в select и конкурирующая форма удалены. Матрица, история, реквизиты и сравнение открываются дополнительно; сам документ не пересоздаётся при открытии вспомогательной панели.

Адрес: /#/acts/{act_id}?section=queue (либо work/preparation/approved), дополнительные panel=matrix/history/details, comment={id} и version={id} для исторической версии из timeline. Hash URL работает при прямом открытии без серверного rewrite. F5 требует повторного входа (JWT не сохраняется), затем сервер снова проверяет доступ. Browser Back работает. Возврат назван по исходному разделу.

Фильтры/страница/scroll сохраняются отдельно для каждого раздела и пользователя в sessionStorage (без JWT и документов). Возврат из карточки восстанавливает список, а не сбрасывает всё на первую страницу. Новая версия для согласующего определяется его активной задачей, для «Согласованных» — действующей публикацией. Историческая версия не позволяет принять решение; POST decision передаёт versionId, и сервер после блокировки проверяет его соответствие циклу задачи. Старый контракт без versionId остаётся связан с конкретным task_id.

При возврате диалог перечисляет сохранённые замечания своей задачи. Общая причина необязательна, когда замечания есть: отправляется ссылка-сводка по сохранённым замечаниям, не их повторный ручной ввод. Без замечаний причина обязательна; прежняя серверная проверка не ослаблена. Повторные нажатия блокируются; серверные idempotency/блокировки/unique решения сохранены. При ошибке назначения/версии/закрытия UI обновляет задачи и карточку и показывает причину.

## Состояния и сохранность работы
CENTRAL_COLLECTING = «Сбор замечаний», этап «Проверка служб продолжается»; RETURNED = «На доработке». Просрочка — дополнительный флаг, не замена основного состояния. Матрица использует ту же трактовку, включая просроченную задачу РИРУ на доработке.

Фоновый опрос каждые 15 секунд не переоткрывает файл, не меняет выбранную версию/масштаб/документ и не очищает ввод. Список замечаний для renderer стабилизирован по содержимому: неизменившиеся записи не приводят к пересозданию маркеров и потере выделения. Несохранённая форма замечания и объяснение исправления защищены предупреждением при уходе/закрытии вкладки. Это защита от случайного ухода, не автосохранение черновика на сервере.
