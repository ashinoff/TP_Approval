# Самостоятельный запуск TP_Approval на Amvera

Вход по логину и паролю, без SUE_system и Keycloak. Это обычные учётные записи с данными в PostgreSQL, не демостенд. Docker-образ по умолчанию использует `AUTH_MODE=local`; API и собранный интерфейс обслуживаются одним контейнером на порту 3000.

## Первый запуск

1. Создать отдельную базу PostgreSQL для TP_Approval. Не использовать базу учёта ПУ или Keycloak. Понадобится служебное подключение с правом создания ролей и таблиц.
2. Подключить этот репозиторий к приложению Amvera. В репозитории подготовлены `Dockerfile` и `amvera.yml`: порт 3000, постоянное хранилище `/data`. На первом этапе использовать одну реплику приложения.
3. Добавить три **секрета этапа «Запуск»**:

| Название | Значение |
|---|---|
| `DATABASE_URL` | `postgresql://tp_runtime:СВОЙ_ПАРОЛЬ@ХОСТ:5432/БАЗА_TP_APPROVAL` |
| `MIGRATION_DATABASE_URL` | Служебная строка подключения к **той же базе**, от владельца с правом `CREATE ROLE` |
| `INITIAL_ADMIN_PASSWORD` | Свой временный пароль администратора, от 12 до 128 символов |

В `DATABASE_URL` укажите `tp_runtime` и выбранный вами непустой пароль. Можно сохранить ранее выбранный пароль: отдельного ограничения в 16 символов для подключения к БД больше нет. Скрипт создаст эту роль и установит указанный пароль; вручную создавать её или переименовывать существующего пользователя БД не нужно. Специальные символы в строках подключения нужно URL-кодировать. Не подставлять в `DATABASE_URL` владельца или суперпользователя: API специально откажется работать с такими полномочиями.

Если в Amvera включён Superuser Access, для `MIGRATION_DATABASE_URL` используйте пользователя `postgres` и пароль из поля «Пароль для Superuser». Пользователь, заданный в поле «Имя пользователя» (например, `admin`), — другая учётная запись БД. Пароль веб-входа из `INITIAL_ADMIN_PASSWORD` также задаётся отдельно; его минимальная длина остаётся 12 символов.

4. Выполнить сборку и запуск. Подготовка применяет SQL-миграции и создаёт первого технического администратора. Логин по умолчанию — **`admin`**. На первом входе приложение попросит заменить временный пароль.
5. После успешного первого входа удалить `MIGRATION_DATABASE_URL` и `INITIAL_ADMIN_PASSWORD` из настроек Amvera и перезапустить контейнер. Для запуска интерфейса и входа останется только `DATABASE_URL`. При последующих обновлениях с новыми миграциями временно вернуть служебное подключение; существующий пароль администратора повторная подготовка не меняет.

Дополнительно, только если нужно: `INITIAL_ADMIN_LOGIN`, `INITIAL_ADMIN_NAME`. `HOST`, `PORT`, `WEB_PATH`, `STORAGE_PATH`, `AUTH_MODE`, `TRUST_PROXY_HOPS` уже настроены в Dockerfile. Для местного запуска без Docker параметры из Dockerfile автоматически не появляются: заполнить `.env`, выполнить `npm ci`, `npm run db:setup-local`, затем `npm run dev:api` и `npm run dev:web`.

## Сотрудники и доступ

После входа администратора открывается раздел «Пользователи». Указать ФИО, уникальный логин латиницей, email, временный пароль и роль; для инженера РИРУ, Начальника РИРУ и Начальника РЭС обязательно выбрать РЭС. Email вводится такой же, как в Keycloak, приводится к нижнему регистру и проверяется на повторение среди неудалённых учёток. У существующих сотрудников и первого администратора email изначально может отсутствовать: заполнить его кнопкой «Изменить». Сотрудник меняет временный пароль при первом входе.

Кнопка «Изменить» позволяет исправить ФИО, логин, email и весь набор ролей/РЭС. Можно добавить или убрать назначение. Смена логина, email или ролей завершает сеансы сотрудника; после изменения своей почты администратор входит заново. При одновременном редактировании сохранится одна версия, второй администратор получит предложение обновить список. Сброс пароля и закрытие доступа остаются отдельными действиями. Самостоятельное восстановление забытого пароля не добавлялось.

«Удалить» требует подтверждения, удаляет парольные учётные данные и сеансы, закрывает доступ и убирает пользователя из списка. Пользовательский UUID, ФИО, ссылки из документов, решения и аудит сохраняются; снятые роли остаются как исторические записи. Повторно можно создать учётку с тем же логином/email, но она получит новый UUID и не станет прежним автором документов. Свою учётку удалить и снять у себя TECH_ADMIN нельзя. Удаление сотрудника/снятие роли с незавершёнными задачами либо действующим или будущим замещением блокируется до завершения этих задач/замещений. Автоматического переназначения или согласования вместо сотрудника нет.

Технический администратор управляет пользователями и не получает доступ к актам автоматически. Для работы с документами нужны отдельные реальные исполнители: инженер → Начальник РИРУ → Начальник РЭС → СТП/СУЭ/ТЕХБЛОК. Существующие проверки РЭС, самосогласования, истории и версий сохранены. Ключи сессий не хранятся в localStorage; cookie закрыта для JavaScript, в рабочем режиме требует HTTPS. Сессия действует 8 часов и сохраняется после F5 и перезапуска сервера.

## Обновление уже работающего приложения: email и управление учётками

Эта доработка требует миграции `016_account_profiles.sql`; файлы001–015 не изменялись.

1. Если `MIGRATION_DATABASE_URL` удалена, временно вернуть её прежнее значение в Amvera, этап «Запуск», «Это секрет». `DATABASE_URL` и пользовательские пароли оставить прежними. `INITIAL_ADMIN_PASSWORD` для существующих учёток не требуется.
2. Собрать актуальную версию репозитория и запустить контейнер. Штатная подготовка применит новую миграцию и сохранит существующие учётки/пароли.
3. Проверить раздел «Пользователи», затем удалить `MIGRATION_DATABASE_URL` и перезапустить контейнер.

Без миграции вход и прежние рабочие разделы продолжают работать, а раздел управления учётками выводит понятное сообщение о необходимости обновления БД. Успешная сборка сама миграцию не применяет.

## Что нужно для работы с документами

**Встроенный антивирус (по умолчанию в Docker-образе).** Образ содержит ClamAV: entrypoint запускает `clamd` только на 127.0.0.1:3310, сигнатуры хранятся в `/data/clamav` и обновляются `freshclam` 12 раз в сутки; `CLAMAV_HOST=127.0.0.1` задан в образе. Нужен тариф не меньше «Стандартный» (2 ГБ RAM), лучше «Стандартный CPU» (2,5 ГБ). Первый запуск дольше на несколько минут из-за загрузки сигнатур. Для внешнего сканера переопределить `CLAMAV_HOST`.

**Внешний сканер (альтернатива).** Подключить ClamAV и указать `CLAMAV_HOST` — внутренний адрес сервиса сканирования. Порт по умолчанию 3310, при необходимости задаётся `CLAMAV_PORT`. Готовый проект сканера для Amvera — [infra/clamav](../infra/clamav/README.md). Сканер не входит в Docker-образ приложения. Его нельзя публиковать как незащищённый TCP-сервис в интернет.

Без сканера можно открыть интерфейс, настроить сотрудников и читать уже сохранённые документы, но загрузка актов и извлечение реквизитов ТУ вернут понятную ошибку. Отсутствующий, недоступный или отклонивший документ антивирус не заменяется разрешением на загрузку. Демонстрационный режим для рабочих документов не использовать.

Перед реальным согласованием назначить всех исполнителей и загрузить утверждённый производственный календарь через существующий API `/api/v1/admin/calendar` от глобального `PROCESS_ADMIN`. Автоматического заполнения рабочими буднями нет: оно исказило бы сроки. Экран редактирования календаря в эту доработку не входит. Пробелы календаря и неоднозначные назначения блокируют отправку, как и прежде.

Файлы записываются в `/data/storage`, вне web-root. При старте entrypoint создаёт папку на подключённом постоянном томе и запускает API от `node`. База и файлы должны резервироваться вместе. Если в другой установке уже есть файлы в прежнем пути `/app/storage`, сначала перенести их штатно в постоянное хранилище; смена пути сама файлы не копирует.

## Проверка запуска

- `/health` возвращает `status: ok`.
- `/ready` проверяет доступ к схеме БД; `uploadsConfigured` означает наличие настройки антивируса, не подтверждает живую доступность сканера.
- Открыть HTTPS-домен приложения: должна появиться форма «Логин / Пароль», затем раздел пользователей для администратора.
- Создать сотрудника, проверить первый вход, смену пароля, F5 и повторный запуск контейнера.
- Проверить DOCX только после подключения антивируса. Документы чужого РЭС должны оставаться недоступными.

Если прокси меняет заголовок `Host` и вход сообщает о несовпадении адреса, явно задать `APP_ORIGIN=https://домен-приложения` и перезапустить контейнер. Не отключать проверку Origin или CSRF. `TRUST_PROXY_HOPS=1` рассчитан на один доверенный прокси перед контейнером; при другой топологии его нужно настроить отдельно.

## Проверки этой доработки

Автоматические проверки: `npm run build`, `npm run build:setup`, `node --import tsx --test tests/*.test.ts`, `npm run test:integration`, `npm run test:standalone:browser`. Последняя команда запускает изолированную PostgreSQL, HTTPS и настоящий Chromium, создаёт только синтетических сотрудников, проверяет смену пароля, F5 и полный restart БД/API. Нужны установленный Chromium Playwright и `openssl`; запуск PostgreSQL — от непривилегированного пользователя. Добавлен workflow `.github/workflows/standalone.yml` для проверки в GitHub Actions после публикации PR.

Фактически выполненные результаты и ограничения текущей среды фиксируются в начале [PROGRESS.md](PROGRESS.md). Наличие теста или workflow не означает, что он уже прошёл. Развёртывание на Amvera и живой ClamAV проверяются отдельно. Прежние ограничения DOCX-просмотра и печати описаны в [SOFTWARE_SUMMARY.md](SOFTWARE_SUMMARY.md).

## Позднее подключение платформы

Режим `AUTH_MODE=keycloak` сохранён с прежними проверками JWT. Email в учётках подготовлен для будущей привязки платформенных пользователей; само заполнение почты не включает вход через Keycloak и не присваивает платформенные роли. Локальные и платформенные личности не склеиваются автоматически по имени, логину или email: при интеграции нужно отдельно связать идентификаторы с сохранением пользователей, актов и истории. Код SUE_system и настройки Keycloak эта доработка не меняет.

Официальные справки: [Docker и постоянное хранилище Amvera](https://docs.amvera.ru/applications/configuration/docker.html), [переменные и секреты](https://docs.amvera.ru/applications/configuration/variables.html).
