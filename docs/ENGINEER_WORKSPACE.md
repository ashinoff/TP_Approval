# Рабочее место инженера и сверка ТУ — 02.11.2026

## Подтверждённое задание
Для инженера четыре основных меню: «Загрузка документа», «На согласовании», «Не согласованные», «Согласованные». Инженер не получает дублирующую персональную очередь согласующего. У совмещающего роль согласующего пользователя она сохраняется дополнительно, чтобы задачи не терялись.

Загрузка содержит форму карточки, выбор акт ТП / АВТУ / ТУ к существующему акту, основной DOCX, сопутствующие ТУ, собственные реквизиты ТУ отдельно от номера договора. Можно сохранить пустой черновик. После загрузки открывается карточка того же раздела с проверкой и отправкой. Загрузка версии переиспользует document-upload.ts, не дублирует workflow. При частичном сбое карточка остаётся сохранённой, ID показан в форме; повторное нажатие не создаёт ещё одну карточку.

## Разделы API
- upload: доступные инженеру черновики DRAFT; форма и черновики на одном экране.
- progress: RIRU_REVIEW / RES_REVIEW / CENTRAL_REVIEW / CENTRAL_COLLECTING. Сбор замечаний ещё не завершённый возврат.
- corrections: RETURNED / REVISING, включая версии, загруженные до новой отправки.
- approved: фактическая CURRENT / UNDER_REVISION публикация. При пересмотре предыдущая утверждённая редакция остаётся здесь, работа над новой — в corrections. REVOKED не выдаётся как действующая.

Выборки/counts вычисляются сервером с RLS и областью РЭС, не по цвету статуса. Legacy preparation API сохранён для совместимости, в основном меню инженера не показывается. Фильтры/страница/прокрутка по каждому разделу отдельны. Непрочитанные уведомления не смешиваются со счётчиками разделов или badge платформы. /me отображает уже действующие временные роли, серверные полномочия не расширяются.

## Проверка перед отправкой
Миграция 012: acts.tu_check_required=true по умолчанию для всех актов и app.tu_checks с FORCE RLS, INSERT/SELECT без UPDATE/DELETE для runtime. Runtime не может отключить обязательность триггером БД; пользовательский API не принимает этот флаг. Изменение маршрута, порядка согласующих, самосогласования, замещения и публикаций не вводится.

POST /api/v1/acts/:id/check-tu {versionId,expectedRevision}, Idempotency-Key. Только инженер своей области и состояния подготовки. Из приватных файлов читаются фактические DOCX с проверкой SHA-256; вывод содержит обе цитаты, part/blockId, версию правил и ссылки на версии/ТУ, автора/время. Отчёт добавляется в историю и аудит. GET карточки возвращает checks (до 100 последних). Кнопка проверки показывает таблицу; отправка в интерфейсе сначала запускает проверку. Прямой POST submit повторно проверяет наличие подходящего PASS и фактические хеши в той же транзакции с блокировкой акта. Замена версии/ТУ не позволяет использовать результат другого комплекта. Без ТУ — TU_REQUIRED; без актуального успешного отчёта — TU_CHECK_REQUIRED. Несовпадения не создают цикл/задачи.

Первые локальные правила DOCX_CONTEXT_V1 без ИИ:
1. Номер договора из контекстного заголовка сравнивается между документами и с карточкой, нули/суффиксы сохраняются.
2. Максимальная мощность всего, не существующая/увеличение/генерация. Точное рациональное приведение кВт/Вт, без float.
3. Класс/уровень напряжения, кВ/В, точное сравнение.
4. Адрес по исходной фразе с осторожной нормализацией пробелов/пунктуации.
5. Текст точки присоединения; совпадение только кода ТП не означает эквивалентность границ.

MATCH / DIFFERENCE / UNKNOWN / MANUAL_REVIEW. PASS только если все пять MATCH. Повторяющиеся разные значения, отсутствующие реквизиты и отличающиеся формулировки не превращаются в успех. Это ограниченный извлекатель по контекстным абзацам, не универсальный импорт DOCX и не полная инженерная экспертиза. Табличные значения в отдельных ячейках пока могут остаться UNKNOWN. PDF/сканы/OCR и Word-редактор не реализованы. Текст сверх 200000 символов отклоняется текущими правилами.

## Ручная проверка — решено 04.11.2026 (Р4)
Спорные пункты (MANUAL_REVIEW) и нераспознанные (UNKNOWN) подтверждает Инженер РИРУ кнопкой «Подтвердить вручную» во вкладке «Сверка с ТУ», с обязательным комментарием. Подтверждение хранится в app.tu_check_confirmations (миграция 014), неизменяемо, привязано к отчёту текущей версии и ТУ и видно согласующим. Расхождение (DIFFERENCE) подтвердить нельзя. Отправка разрешена, когда расхождений нет, а спорные пункты подтверждены. Правила DOCX_CONTEXT_V4 дополнительно сверяют заявителя, номер ТУ, существующую/присоединяемую мощность, питающий центр, наименование ЭПУ и подпункты ТУ; читают колонки таблицы «Перечень точек присоединения» и уровни нумерации Word. Категория надёжности — только для сведения.

## Ручная проверка — прежняя запись (история)

Пользователю задан вопрос: кто подтверждает нераспознанные/неоднозначные значения — инженер с фиксацией либо Начальник РИРУ. Ответ пока не получен. Ни одного ручного обхода не реализовано: UNKNOWN / MANUAL_REVIEW тоже блокируют отправку. Известное DIFFERENCE нельзя обойти. Не выдавать это за полноценную поддержку всех реальных шаблонов; следующий шаг — согласовать ручной контроль и добавить точное извлечение табличных реквизитов на обезличенных шаблонах.

## Тестовые данные
Прежние регрессии используют минимальные синтетические DOCX без реквизитов ТУ. Их owner-fixture явно помечает tu_check_required=false только в изолированной тестовой БД / synthetic demo с проверкой marker. API/runtime сделать это не могут. LEGACY — явное отсутствие проверки, не PASS. Новые engineer.integration/browser тесты создают обычные карточки с обязательной проверкой, используют полноценные обезличенные DOCX и проверяют реальную блокировку. Не распространять legacy-exemption на реальные акты и не считать старые тесты доказательством проверки ТУ.
