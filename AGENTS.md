# TP_Approval — постоянные инструкции

## Назначение и границы
Реальная система согласования актов технологического присоединения Сочинского ПЭС: документы, версии, замечания, маршруты, сроки, уведомления, аналитика и интеграции. Общаться исключительно на русском языке.

## Обязательное начало каждой сессии
1. Прочитать этот файл, `docs/PROJECT_CONTEXT.md`, `docs/PROGRESS.md`, `docs/IMPLEMENTATION_PLAN.md`, `docs/DECISIONS.md`.
2. Проверить текущий каталог, `git status --short --branch`, текущую ветку и последние коммиты. Для пустого репозитория отсутствие HEAD нормально.
3. Сопоставить фактический код с журналом; продолжать последний незавершённый шаг, не выдавая планы за реализацию.
4. Изучить вложенные AGENTS.md перед изменениями соответствующих каталогов.

## Разработка
- Интерактивные DOCX: читать docs/DOCX_PROTOTYPE.md. Вкладка «Документ» пока явно маркированный docx-preview-прототип, не промышленная точная вёрстка Word/ONLYOFFICE. ONLYOFFICE не установлен/не проверен. Не убирать маркировку и не включать печать DOCX до fidelity-теста и надёжного генератора. Anchor OOXML_PARAGRAPH_V1 относится только к исходной версии/хешу; не переносить его на новую редакцию эвристически. Миграции 007/008 уже применяются к синтетическому стенду: не редактировать. Проверять test:documents:browser и test:documents:persistence (после restart), реальное выделение и изоляцию РЭС.
- Архитектура утверждена пользователем 31.10.2026 с уточнениями в PROJECT_CONTEXT. Разрешена реализация и проверка рабочего ядра; push, Amvera и боевые изменения требуют отдельного разрешения.
- Предлагаемый стек: TypeScript, React/Vite; Node.js/Express; PostgreSQL с SQL-миграциями и RLS; Python-сервис документов (python-docx, PyMuPDF); локальный ONLYOFFICE Docs после технической проверки; Docker. Точные версии и лицензии проверить при реализации, зависимости фиксировать lock-файлами.
- Не изменять бизнес-логику согласования без согласования с пользователем. Каждый новый цикл проходит Начальника РЭС, затем СУЭ/СТП/ГИ; предыдущие решения не переносить.
- Матрица согласования — read-only derivation реальных записей (docs/APPROVAL_MATRIX.md), не новая копия статусов. Миграция 005 сохраняет личность исполнителя; завершённые строки не пересчитывать по текущему профилю/замещению. Отсутствие решения не превращать в согласование.
- Центральный сбор продолжается после RETURN. PROCESS_ADMIN своей области может закрыть просроченный сбор с причиной, без фиктивных согласований. TECH_ADMIN не получает доступ к актам автоматически.
- Назначения учитывают РЭС/подразделение и датированное замещение. Самосогласование и решения в разных ролях по одному акту запрещены, включая историю циклов. Устранение подтверждает автор замечания при повторном согласовании.
- Не создавать фиктивные API, демонстрирующие несуществующую работу. Тестовые данные только синтетические и явно обозначенные.
- Для локальной браузерной проверки использовать `npm run demo` и docs/LOCAL_BROWSER_GUIDE.md: отдельный PostgreSQL, локальный подписывающий JWT-сервис, синтетические пользователи/документы. Не подключать боевой Keycloak или существующие БД. Демо-ключи, данные и отчёты находятся в исключённой из Git .local. Перезапуск не должен сбрасывать БД.
- Браузерную проверку считать выполненной только при реальном запуске браузера; различать headless Chrome, ручной GUI-тест и проверку API. Фактические отчёты — .local/browser-report; production SSO и форматирование Word/ONLYOFFICE этим стендом не подтверждаются.
- SUE_system только исследовать; изменения его кода требуют отдельной задачи. Не переносить туда бизнес-логику.
- Никакого самовольного развёртывания, изменения боевой инфраструктуры или push. Существующие изменения пользователя сохранять. Разрушительные команды требуют разрешения. Коммит не обязателен в каждой сессии.

## Безопасность
- JWT проверять на сервере; роли и область РЭС брать из собственной БД. Проверять права на каждый вложенный ресурс, файл, отчёт, экспорт и фоновое задание.
- RLS — дополнительная защита БД, runtime без superuser/BYPASSRLS/владения таблицами. Пользовательский контекст только в транзакции; не допускать утечки через пул соединений.
- Хранить файлы вне web-root, ограничивать загрузку, проверять содержимое и ZIP-структуру DOCX, карантин/антивирус, исключать SSRF, макросы и опасные внешние связи.
- Не помещать в Git секреты, JWT, ПДн, реальные DOCX/PDF, дампы, резервные копии, виртуальные окружения. Не передавать ПДн внешним AI API без отдельного разрешения и политики.
- Исходные и поданные версии неизменяемы; решения и аудит сохраняются. Электронное согласование не является ЭП.

## Проверка и завершение этапа
- Проверить diff и отсутствие секретов; выполнить доступные проверки, относящиеся к изменениям. Для кода: типы, lint, сборка, модульные и интеграционные тесты; для маршрутов — конкуренция, повторные запросы, права и сохранение истории; для RLS — реальные запросы под runtime-ролью.
- Для документации проверить ссылки, взаимную согласованность и полноту; не утверждать, что сборка/тесты пройдены, если приложения ещё нет.
- Обновлять PROJECT_CONTEXT, PROGRESS, IMPLEMENTATION_PLAN после значимых изменений; важные решения и их статус — в DECISIONS. В PROGRESS: дата, задача, файлы, проверки, проблемы, остаток, конкретный следующий шаг, решения пользователя.
- Перед исчерпанием контекста оставить достаточно фактов для продолжения. Не заменять неизвестное предположениями; отделять требования, проверенные факты, предложения и открытые вопросы.
