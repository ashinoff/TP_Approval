# TP_Approval — ключевой контекст

Короткая выжимка того, что нужно знать перед любой работой. Подробный журнал — [docs/PROJECT_CONTEXT.md](docs/PROJECT_CONTEXT.md) и [docs/PROGRESS.md](docs/PROGRESS.md), постоянные правила — [AGENTS.md](AGENTS.md). Обновлять этот файл при каждом значимом изменении: дата, что сделано, что важно помнить.

## Что это
Согласование актов технологического присоединения Сочинского ПЭС. Деловой ключ — номер договора ТП; пакет: ТУ + Акт ТП / АВТУ.
Маршрут: Инженер РИРУ → Начальник РИРУ своего РЭС → Начальник РЭС → параллельно СТП, СУЭ, ТЕХБЛОК. Бизнес-логику маршрута не менять без согласования с владельцем.

Стек: React/Vite/TypeScript, Node.js/Express, PostgreSQL (SQL-миграции + RLS), файлы на постоянном томе, ClamAV внутри контейнера.

## Где работает
- **Amvera, регион Miami:** приложение `tp-approval` (Docker, тариф ≥ 2 ГБ RAM — нужен ClamAV), БД `tp-approval-db` (CNPG). Вход — локальные логин/пароль (`AUTH_MODE=local`), Keycloak не используется.
- Постоянный том `/data`: `/data/storage` — документы, `/data/clamav` — антивирусные базы.
- **Push в `main` → Amvera сама пересобирает.** С 04.11.2026 изменения отправляются сразу в `main` (без PR, решение владельца); после пуша проверяются логи сборки и запуска. Слияние PR через веб-интерфейс автосборку не запускало — тогда «Пересобрать» вручную.
- Режим: **тестирование** — реальных документов и ПДн пока нет, лишнее можно удалять.

## Переменные Amvera
| Переменная | Когда | Зачем |
|---|---|---|
| `DATABASE_URL` | всегда, секретом | подключение под `tp_runtime` — без прав менять схему |
| `MIGRATION_DATABASE_URL` | **только** на время пересборки с новой миграцией, потом удалить | подключение владельца схемы (`postgres`), чтобы применить новые файлы `db/migrations/NNN_*.sql` |
| `INITIAL_ADMIN_*` | только первый запуск пустой БД | создание первого администратора |
| `ADMIN_RESET_PASSWORD` | только вместе с `MIGRATION_DATABASE_URL`, на один запуск | сброс пароля учётки `admin` (снимает блокировку и требование смены). После входа удалить обе переменные, иначе пароль сбрасывается при каждом перезапуске |
| `CLAMAV_HOST` | не задавать | в образе уже `127.0.0.1` |

**Миграция** — SQL-файл, меняющий структуру БД (новые таблицы/колонки/правила доступа). Рабочий пользователь `tp_runtime` намеренно не может менять схему, поэтому при обновлении с новой миграцией нужен временный `MIGRATION_DATABASE_URL`. Если в обновлении нет нового файла в `db/migrations/` — переменная не нужна. Применённые миграции не редактировать, только добавлять новые.

## Обновление на Amvera
1. Если в изменении новый файл в `db/migrations/` — **до пуша** временно добавить `MIGRATION_DATABASE_URL`.
2. Push в `main` (сборка стартует сама). Признаки успеха в логе запуска: `Миграции применены…` (если была миграция) и `TP_Approval: порт 3000, вход local`.
3. Удалить `MIGRATION_DATABASE_URL`, перезапустить.

## Работа с Git на этой машине
Обычный `git push` не проходит (в `~/.gitconfig` helper `store`). Работает: `git -c credential.helper= -c credential.helper=manager push …`. `gh` не установлен — PR открывается по ссылке `https://github.com/ashinoff/TP_Approval/pull/new/<ветка>`.

## Планы развития (обсуждено 04.11.2026, не реализовано)
1. ~~Формат номера договора ТП~~ — сделано в этапе 1, исключений нет.
2. **Расширяемая карточка документа** — справочник полей (название, тип, обязательность, формат, источник из ТУ), администратор добавляет поля без миграций. Четыре базовых поля (договор, дата, заявитель, адрес) остаются колонками. Значения привязаны к версии документа и неизменны после согласования. Решено: из ТУ читаются мощность, напряжение, фазность; инженер вручную вводит только планируемую дату исполнения. Позже: поопорная схема, данные питающего центра (мощность трансформатора, пики лето/зима — вероятно, из программы мониторинга напряжения), синхронизированный номер ПУ.
3. **Синхронизация с «Учётом ПУ» (последний шаг)** — TP_Approval отдаёт по служебному ключу реквизиты договоров; в карточке ПУ (техприс) номер договора выбирается из списка, остальное подставляется, ввод несуществующего договора невозможен. Поля «Светлячка»: `contract_number`, `contract_date`, `consumer`, `address`, `power`, `voltage`, `faza`, `plan_date`. Решено: только согласованные.

4. **Режим проверки (два окна)** — эталон `картинки для интерфейса/Сравнение акта и технических условий.png`: слева проверяемый акт/АВТУ (замечания только к нему), справа ТУ или другой документ пакета только для просмотра, панель замечаний и автосверки. Инженер до отправки только сверяет (без замечаний), согласующие оставляют замечания.
